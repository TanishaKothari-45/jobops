Agent Engineer Curriculum

The skills AI-native companies are actually hiring for, drawn from live job postings — organised into fourteen labels, twelve modules, and nine small projects that each prove one of them.

Built from real postings, Sep 2026Target: applied AI / AI engineer, junior–mid

01 Three role shapes, one spine

“Applied AI Engineer” means three noticeably different jobs depending on the company. Here is what each actually says, in their own words.

Sarvam AI
“Flow design, prompting, tool definitions, memory systems, evaluation, and deployment… state handling, retries, and scheduled execution.”
Agent product builder
Wispr Flow
“Build end-to-end verification loops that let agents determine when their work is actually complete… turn failures and human feedback into durable evaluation signals.”
Agent infrastructure & eval
Emergent
“Work directly with business users to translate problems into working apps… think in systems, with focus on data flows, edge cases, and user outcomes.”
Forward deployed

Different emphases — but notice what none of them ask for: training a model, publishing research, or inventing an architecture. Every one is a backend engineering job where the payload is an LLM, judged on whether the thing you shipped stays up and gets measurably better.

The sentence that decides most applications

Sarvam: “Shipped AI features to real users in production, not just notebooks or prototypes.”
Wispr Flow: “You've built internal tools that other engineers adopted, and you can explain how you measured their impact.”

Both are the same filter written twice: did it reach someone, and can you prove it worked? A curriculum that ends in demos fails this filter. So every project below ends in a number, a trace, or a user.

One tool layer, three surfaces

The architecture that makes all of this fit together. We write the tool layer once and point it at three different faces — which is why a month is enough.

            Core: tool layer + domain services
        search_jobs · read_application · draft_message …
                            │
        ┌───────────┴────────────┴──────────────┐
   Seeded world          Real backend          MCP server
   (evals, CI)        + your agent loop     stdio → HTTP
   graded                traced, versioned     Claude / ChatGPT
                         crash-resumable       / Gemini call it

The MCP server is a thin wrapper — roughly 150 lines over tools you were writing anyway. But it matters that it is a third surface and not the whole product: an MCP host supplies the model and the loop, so if that were the only thing you built, you would own no agent to version, trace, make resumable, or evaluate. Modules M1, M3, M4, M8, M9 and M11 would have nothing to grade.

02 The fourteen labels

Four tiers. Tier 0 is ordinary software engineering — not optional, and where most self-taught AI portfolios quietly fail. Tier 3 is what separates a mid-level hire from a junior one.

03 What we deliberately skip

  • Model training, fine-tuning, PyTorch. None of these postings ask for it; Wispr Flow says so explicitly. It's a different career.
  • Heavy DSA grinding. Not one of these JDs mentions algorithms — they mention Postgres and observability. Keep enough warm to survive a 45-minute screen; spend nothing more.
  • Kubernetes depth, MLOps platforms, distributed training. Adjacent jobs, not this one.
  • Framework tourism. Knowing LangGraph well beats knowing six frameworks shallowly. Nobody asks which you used; they ask what broke.

04 Twelve modules, nine small projects

Each module is lessons first, then a small build — nothing gets built before its concept page exists. Projects stay small: two to five days each, one clear thing proved per project. The last assembles the pieces.

Phase 1 · The measurement spine
M1Eval foundationsK
What an eval is · offline vs online vs A/B · unit vs trajectory · outcome vs process grading · the three grader families · contamination, saturation, overfitting.
No build
Concepts only. Lesson already written.
Status: complete.
M2Environment designK · B
Deterministic tool mocks · seeded world state · the reset / step / done interface · trajectory logging · task templating and difficulty · reward hacking.
Project 1
A seeded support-ops world with ~8 tools, full trajectory capture, and a state-diff grader. No LLM anywhere in the grading path.
Proves: you can build the thing agents get scored in — the rarest item on the list.
M3Graders & judgesK
Programmatic graders · partial credit · LLM-as-judge mechanics, rubric decomposition, position and verbosity bias · calibrating a judge against your own labels · variance, and why one run is never evidence.
Project 2
Add a judge for the one slice code can't decide, hand-label 100 examples, measure agreement, and report scores with a confidence interval.
Proves: you can answer “how do you know your judge is right?” — most candidates can't.
Phase 2 · The agent itself
M4LLM API fluency, properlyD · E
Structured outputs and schema enforcement · function calling · streaming · handling malformed output · token accounting · prompts as versioned artefacts.
Project 3
A prompt registry: prompts versioned in git, run against the M2 task suite, two versions compared side by side, one rolled back on a regression.
Proves: “prompt iteration workflows with versioning, A/B testing and safe rollback” — Sarvam's exact phrase.
M5Tool layer & MCPG
What makes a tool definition a model uses correctly · MCP architecture · stdio vs Streamable HTTP transports · resources vs tools · running a server · tool-call failure modes.
Project 4
Write and run your own MCP server over stdio, exposing the same tool layer — then add it to Claude Desktop and use it daily from week 2. Your own usage becomes the source of real task ideas.
Proves: built MCP, not just consumed it. Sarvam asks for MCP infrastructure at scale.
M6Memory & context engineeringH
Working vs long-term vs retrieval memory · compaction and summarisation · what to keep, drop or re-fetch · context rot over long horizons · measuring whether memory actually helped.
Project 5
A memory layer on Postgres + Redis, then an A/B on the M2 suite: the same agent with and without it, scored.
Proves: Wispr Flow's “enhance how context and memory are delivered to agents while measuring performance improvements.”
M7Retrieval that isn't naiveI
Chunking strategies and why they matter more than the model · embeddings · hybrid search (keyword + dense) · reranking · where your existing RAG metrics fit.
Project 6
Upgrade a retrieval service to hybrid + rerank, and publish the before/after on context precision, recall and faithfulness.
Proves: the exact RAG bullet in Sarvam's requirements, with numbers attached.
Phase 3 · Production behaviour
M8ReliabilityJ · A · B
Idempotency keys · retries with backoff and jitter · durable run state · resuming after a crash · scheduled execution · partial-failure recovery · promoting the MCP server to Streamable HTTP with OAuth 2.1 so other people can connect to it.
Project 7
Make an agent run survive being killed mid-flight: persist state, resume, and prove no double-refund by killing it during a tool call.
Proves: Sarvam's “state handling, retries, and scheduled execution” — with a demo that is genuinely hard to fake.
M9ObservabilityL · M
OpenTelemetry spans over an agent run · what belongs in a span · structured logs · cost and latency as first-class metrics · p95 vs average · drift alerting.
Project 8
Trace every run end to end, then a dashboard showing cost per task, p95 latency, and score — three numbers on one screen.
Proves: the observability requirement, and gives you the cost dashboard hiring guides explicitly name.
M10Guardrails & safetyN
Prompt injection arriving through tool results · approval gates on irreversible actions · output validation · audit trails · why blocklists fail.
Bolt-on to project 7
An approval gate on anything irreversible, plus an injection test suite added to the M2 tasks as adversarial variants.
Proves: “an agent with human approval on irreversible actions” — a named portfolio item in 2026 hiring guides.
M11CI & the regression gateK · C
Evals in CI · choosing a threshold · handling flaky evals · dataset versioning · the held-out slice in practice.
Bolt-on to project 1
A GitHub Action that runs the suite on every pull request and blocks the merge on a regression.
Proves: Wispr Flow's “test harnesses, CI systems, eval pipelines.”
M12Ship it and write it upC · all
Deployment · what a good engineering writeup contains · failure taxonomies · describing impact in numbers.
Project 9 · capstone
Deploy the agent so real people can use it, get five real users, and publish a writeup: what broke, what the failure taxonomy was, what the numbers did.
Proves the sentence that gates everything: shipped to real users, impact measured.

05 Why this order

Measurement first, deliberately. Most people build the agent and bolt on evals once things start breaking. Doing it backwards means every later module — memory, retrieval, reliability, guardrails — gets built against a suite that can already tell you whether it helped.

That one choice turns nine small projects into a single coherent story rather than nine disconnected repos. Everything after M3 produces a before-and-after number, because the measuring stick already exists.

What this looks like on a resume when it's done
  • One deployed agent product with real users — answers “not just notebooks or prototypes.”
  • An eval harness with a calibrated judge and a CI gate — answers “experience building and running AI system evaluations.”
  • A remote MCP server with OAuth that other people's assistants connect to — which is Sarvam's “connector frameworks and OAuth integrations” built rather than claimed.
  • Memory measured A/B, hybrid retrieval with before/after scores, a crash-resumable run, a cost and latency dashboard.
  • A written failure taxonomy — the artefact that reads as senior regardless of years.

06 Three questions before we start M2

  • What should the agent actually do? Support-ops is the default because correctness is machine-checkable — but if you'd rather it be something you'd use daily, the whole curriculum still holds; only the world changes.
  • How many hours a week? Decides whether M1–M12 is a two-month or a five-month plan.
  • Public or private? M12 needs real users. Five people from your network counts.
