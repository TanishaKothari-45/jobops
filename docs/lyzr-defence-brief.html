Lyzr Defence Brief

Nine modules from the assignment, each with the question they will ask and the answer to give. Built for rehearsing out loud, not for reading.

The answer shape — use it every single time

1. What I chose. One sentence, no hedging.
2. Why, in their terms. Reliability, cost, or auditability — not elegance.
3. What I gave up. Name the trade-off before they find it.
4. What I'd change. One real improvement ready per module.

Four beats, thirty to sixty seconds. The brief literally says "explain your decisions, trade-offs and what you would improve" — they have handed you the format. Use it.

Read this before anything else

Lyzr's product is agent infrastructure with Safe AI and Responsible AI modules in the core architecture, and their FDEs "move agents into production with true governance and security."

So every answer should end somewhere near: "…and here is how I would know it was behaving." Most candidates will explain what they built. Almost none will explain how they would catch it going wrong. That is your edge, and it is the thing this company sells.

The nine modules

01Structured outputauditability
They'll ask"The model returns free text. How did you make it structured, and what happens when it doesn't comply?"
AnswerSchema-constrained output, so an invalid shape is unrepresentable rather than caught later. Validate on receipt; on failure, hand the validation error itself back to the model as the next turn — it usually self-corrects in one round. And count those retries: schema-validity rate is a metric, not an accident.
Rejected & costRegex or JSON-parsing free text — brittle and silently wrong. Constrained decoding costs some flexibility and can bias the model into filling required fields with plausible junk, which is why fields get validated for sense, not only for shape.
I'd improveDistinguish malformed from well-formed but wrong. Today both look like failures; only the first is worth an automatic retry.
Cross-ref: my own repo defines all twelve tools as JSON schemas, so one definition serves LLM function calling and an MCP server without rewriting.
02The ReAct loopcontrol
They'll ask"How does the loop terminate? What stops it running forever?"
AnswerFour conditions, not one: it stops calling tools; a hard step cap; a token or cost budget; and no-progress detection when the same call repeats with the same arguments. And I record the stop reason on every run — "it finished" and "the limit finished it" produce identical-looking output and are completely different outcomes.
Rejected & costImplicit termination alone (a turn with no tool calls). Simple, but "let me explain what I found" is indistinguishable from "I have finished the work". An explicit finish step costs one more tool, and the model occasionally forgets to call it.
I'd improveA verification step before the loop may exit — check the work actually happened, rather than trusting the agent's claim that it did.
Cross-ref: my environment enforces a step limit and stores the stop reason, so "ran out of steps" becomes its own failure category in the results.
03Tool calling & concurrencysafety
They'll ask"How many tool calls in parallel? What if two of them conflict?"
AnswerParallelise reads, serialise writes. I band every tool: read-only, reversible write, irreversible. Reads are safe to fan out and safe to retry. Writes need idempotency keys so a retry does the work once. Irreversible actions get an approval gate and never run concurrently with anything.
Rejected & costFull parallelism for latency. Faster — and two writes racing on one record is a data-integrity bug you cannot reproduce. Serialising writes costs wall-clock time, and for a refund that is a trade I will make every time.
I'd improveA concurrency limit per tool rather than one global cap — a search API and a payments API should not share a budget.
Cross-ref: tool errors in my environment go back to the agent as data, not exceptions — so error recovery is something I can score rather than hope for.
04Memory across agentsthe hard one
They'll ask"Multiple agents on one dashboard. Do they share memory? What breaks if they do?"
AnswerSeparate the kinds. Working memory is per-agent, per-run — never shared, it is just that run's state. Semantic facts about a customer should be shared, or two agents tell the same person different things. Episodic history is shared read-only, so an agent can see what another already did and not repeat it.
Rejected & costOne shared pool for everything. Simple, and it is how you get cross-contamination: a billing agent's scratch notes steering a support agent. Separating costs a more complex write path and a real decision about who may write what.
I'd improveProvenance and a TTL on every memory from the first row — which agent wrote it, when, from what source. Retrofitting provenance is impossible; you cannot recover what you never recorded.
If pushed further: the failure that worries me is memory poisoning — something false, or planted in untrusted tool output, written once and then treated as established fact by every agent forever. Because it arrives as memory rather than as input, nothing downstream questions it.
05Model routingcost
They'll ask"How do you decide which model handles a request? What if the cheap one is wrong?"
AnswerCheap model first, escalate on a signal rather than a guess: low confidence, a failed verification, or a task type known to need it. The escalation path is the interesting part — routing is only safe if something checks the cheap answer, otherwise you have simply made errors cheaper to produce.
Rejected & costA classifier up front choosing the model. It adds a call, it is another thing to evaluate, and it is confidently wrong on exactly the edge cases that most need the strong model. Escalation costs double latency on the requests that escalate — acceptable if they are a minority, which is the thing to measure.
I'd improveTrack cost per successful task, not cost per call. A cheap model that fails and escalates is more expensive than going straight to the strong one, and per-call cost hides that completely.
The number that settles this argument: "+3% quality at 2.4× the cost" is the decision a team actually makes. Quality alone is half a metric.
06Human in the loopyour strongest
They'll ask"Where did you put the human, and why there?"
AnswerOn irreversibility and blast radius, not on confidence. A redo costs a little time and can be undone, so the agent proceeds. A refund or a credit moves money and cannot be taken back — that always goes to a human, however sure the model is. Confidence is a bad gate precisely because a confidently wrong refund is the case you are protecting against.
Rejected & costThreshold gating on model confidence — it routes the wrong things, and calibration drifts with every model change. Rule-based gating costs throughput: some approvals are unnecessary and a human waits on them. That is the correct trade for money-moving actions.
I'd improveGraduated gates by amount rather than one binary — auto-approve small credits, queue medium ones, block large ones. And measure how often humans simply rubber-stamp: an approval nobody reads is theatre, not a control.
The line to land: in my own project, approval is a tool the agent must call, not a check hidden in the backend. That makes its judgement about when to ask visible in the trace and gradeable — so a run that reached the right outcome by skipping approval still fails. Outcome grading alone would have passed it.
07The judgeyour strongest
They'll ask"You used an LLM to verify the answer. How do you know the judge is right?"
AnswerYou measure it. Hand-label around 100 examples against the rubric, have a second person label 30 of those to establish the human ceiling, then measure judge-versus-human agreement with Cohen's kappa — agreement above chance. Below roughly 0.4 it is close to guessing and I would not ship it; usually the rubric is ambiguous rather than the judge being stupid. I report the kappa beside the score so people know what the number is worth.
Rejected & costJudging everything with a model. A judge costs money, varies run to run, and carries known biases — position, verbosity, self-preference. So a judge is a fallback for what code cannot decide, never the default. It also cannot do arithmetic, which is where people most often misuse it.
I'd improveJudge with a different model family from the one being judged, to remove self-preference — or a small jury of cheaper models, which dissolves it entirely.
If they push on bias: each one is measurable. Swap the order and diff for position bias; correlate score against length for verbosity; plot the distribution for leniency. "How would you handle judge bias" has a weak answer (list them) and a strong one (here is how I would measure each on my own judge).
08Evaluationgo deepest here
They'll ask"How do you evaluate a system like this?"
AnswerStart from what is decidable. Code that runs → run the tests. Actions that change a system → diff the resulting state. Structured output → validate the schema. Only what is genuinely subjective goes to a judge, and that judge gets calibrated first. Then I grade the trajectory as well as the end state, because policy violations never show up in the outcome.
Rejected & costReading transcripts, or one judge scoring everything. State comparison costs you building a world with real state — which is exactly why I built one.
I'd improveWeighted partial credit. Right now every check counts equally, so "recommended something unqualified" costs the same as "fetched one page more than needed". Those are not the same mistake.
Have these ready: pass@k is whether it can; pass^k is whether it will — all k attempts succeeding. For agents taking real actions, reliability beats capability. And a score with no variance, no dataset version and no prompt version beside it is not evidence.
09Order of attackthey will ask this
They'll ask"Which file did you do first, and why?"
AnswerThe question is not about the file. It is about whether you have a principle. The strongest one: build the thing that tells you whether everything else works, first. Contracts and verification before behaviour — structured output and tool schemas define what every other module passes around, and evaluation is what tells you whether any later change helped. Everything downstream inherits both.
Rejected & costStarting with the loop because it is the most interesting file. You then tune it against nothing, and cannot tell whether a change improved anything.
I'd improveBe honest if you did it in a different order — then say what that cost and what you would do next time. An honest account of a wrong order beats a tidy story nobody believes.
Cross-ref: in my own project I built the environment and graders before any model was involved — so when the model goes in, movement in the score comes from the model, because everything else is already proven.

Three weaknesses to volunteer

They will ask. Answer before they do — it reads as judgement, not as a gap
  1. "My graders weight everything equally." A policy violation and a wasted API call score the same. I know the fix — weighted partial credit — and I have not built it yet.
  2. "I have no calibrated judge yet, only a proxy." I check that a stated reason names the specific role rather than being generic. It catches the obvious failure and it is not a real quality measure. The judge and its kappa come next.
  3. "I have not run this at production volume." I have designed for concurrency and idempotency; I have not watched it under real load. What I would watch first is p95 latency and cost per successful task.

Never say "it's perfect". If you do not know something, say so and say how you would find out — that beats bluffing, and interviewers are far better at spotting bluffing than at spotting gaps.
