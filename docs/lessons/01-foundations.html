Eval Foundations

What an evaluation actually is, why normal software testing breaks on LLMs, and the three ways people grade an agent — before we write a single line of the project.

No maths required~15 minSources at the end

1.1 What an eval actually is

An eval (short for evaluation) is a test suite for software that doesn't give the same answer twice.

That's the whole idea. Everything else is detail.

In normal programming you write assert add(2,2) == 4. It passes or it doesn't, and it behaves identically forever. Run it a thousand times, get a thousand identical results. That repeatability is what makes traditional testing feel solid.

LLMs break it. Ask the same model the same question twice and you get two different sentences that may both be correct, or both wrong, or one of each. There is no == you can write. So instead of a test that asks "is the output exactly this string", you need one that asks "is the output good enough, and how often".

In plain words

Testing normal code is like checking a vending machine: press B4, a Snickers must come out. Every single time. If it doesn't, the machine is broken.

Testing an LLM is like assessing a new employee. You can't check them against one right answer — you give them twenty realistic tasks, see how many they handle well, and form a judgement. If they get 18 out of 20 right this month and 12 out of 20 next month, something changed and you want to know what.

An eval is that set of twenty tasks, written down, run automatically.

So every eval has three parts, however fancy it gets:

  1. A set of tasks — the questions on the exam. Called the dataset, golden set, or task suite.
  2. A thing being tested — your prompt, your model, your whole agent. Whatever you're about to change.
  3. A grader — the thing that decides pass or fail, or gives a score. Also called a scorer, or in reinforcement-learning language a verifier.

When eval engineers talk, they are always talking about one of those three. If you're ever lost in the conversation, silently ask: tasks, thing being tested, or grader?

1.2 Why this became a whole job

Here's what turned evals from a nice-to-have into standalone job postings.

When you build normal software, your bottleneck is writing the code. When you build an LLM product, writing is fast — you change three lines of a prompt in thirty seconds. Your bottleneck becomes knowing whether that change made things better or worse.

Without evals the loop is: tweak the prompt, try five examples by hand, they look fine, ship, and three days later a customer finds it broke something else. You can't iterate quickly because you can't see.

With evals: change the prompt, run 200 tasks in four minutes, get a number. Teams with good evals ship far more versions per quarter — not because they're smarter, but because they can move without fear.

In plain words

It's the difference between cooking with a thermometer and cooking by poking the chicken. Both can work. Only one lets you cook a hundred chickens a day and be confident about all of them — and only one lets a second person reproduce what you did.

1.3 Three places to measure: offline, online, A/B

Our first three-ways choice. These aren't competitors — mature teams use all three at different moments. But knowing which one answers which question is a real interview question.

KindWhat it isAnswersBlind spot
Offline Run a fixed set of saved tasks in your own environment. No real users. "Did my change break anything I already knew about?" Only tests situations you thought of. Real users are more creative than you.
Online Score real production traffic as it happens — cheap automatic checks on everything, a stronger grader on a sample. "Is quality drifting in the real world, right now?" You usually don't know the correct answer for live traffic, so grading is fuzzier.
A/B test Send some real users version A and some version B, compare actual behaviour. "Do humans genuinely prefer the new version?" Slow, needs traffic volume, can't tell you why.
In plain words

Offline is a driving test on a closed course. Same cones, same parking bay, every candidate. Fair, repeatable, cheap — but the closed course has no schoolchildren running into the road.

Online is the dashcam in a real taxi. Messy, unrepeatable, but it's the actual world.

A/B is putting two drivers on the same route for a month and seeing who gets more repeat customers.

Almost all of the engineering skill lives in offline evals, because that's the one you control and the one that runs in CI. That's where this course spends its time.

1.4 Grading one step vs the whole journey

This is the split that separates RAG-era evaluation from agent-era evaluation. Worth being very clear about.

Unit-level eval

You evaluate one model call. Input in, output out, score the output. "Was this summary faithful to the document?" "Did the classifier pick the right label?" "Was the retrieved context relevant?"

Everything you already know from RAG evaluation — context precision, context recall, faithfulness, answer relevance — lives here. It's genuinely useful and it isn't going away. It is just one box in a bigger picture.

Trajectory-level eval

You evaluate an entire agent run: fifteen steps, six tool calls, decisions along the way, and whatever state the world ended up in. Trajectory just means "the full recorded path the agent took" — every message, every tool call, every tool result, in order.

This is the hard one, and where nearly all production agent failures actually live. An agent can produce a beautifully written final message while having called the wrong API, refunded the wrong customer, or silently given up four steps ago.

In plain words

Unit-level eval is marking one line of a student's working. Trajectory eval is marking the whole answer — including noticing they got the right final number by copying it from the back of the book.

The trap

Errors cascade. If step 3 fetched the wrong customer record, steps 4 through 15 all look wrong too. When you read a failed trajectory your job is to find the first step that went wrong — not the last, and not the loudest. Beginners consistently fix the final error and wonder why nothing improves.

1.5 Outcome-based vs process-based grading

You asked to be able to answer this one cold, so here it is properly.

Outcome-based grading

Definition: you ignore how the agent got there and judge only the end result — the final answer, or the final state of the world.

Example: the task is "refund customer 4471's undelivered order." You don't read the transcript at all. You look at the database afterwards: is there a refund row for order 8823, for the right amount, and is the ticket marked resolved? Yes → pass. No → fail.

Where it's used: anywhere the correct end state is well defined. Code generation (do the unit tests pass?), maths (is the number right?), tool-use agents (is the database in the expected state?), SQL generation (does the query return the right rows?). It's the backbone of modern agent benchmarks and of RL reward signals, where it's called a verifiable reward — verifiable meaning a machine can check it without an opinion.

Why people love it: cheap, fast, objective, impossible to argue with. No model needed to grade it. It never has a bad day.

Where it fails: it can't see luck or recklessness. An agent that got the right answer by guessing, or that deleted three unrelated records on the way, scores identically to one that did it properly. And for open-ended work — "write a good apology email" — there's no single correct end state to check against.

Process-based grading

Definition: you judge the path — the reasoning steps, the sequence of tool calls, whether policy was followed.

Example: same refund task. Did the agent verify the customer's identity before discussing the order? Did it check the refund policy before issuing money? Did it escalate rather than approving an amount above its limit? You can pass or fail on these regardless of the final outcome.

Where it's used: regulated domains — finance, healthcare, insurance — where how you reached a decision is legally as important as the decision. Also safety evaluation, multi-step reasoning where you want partial credit, and any time you need to debug why something failed rather than just that it did.

Why people need it: it gives you a gradient. A binary pass/fail on a twelve-step task tells you almost nothing — "it failed" isn't a bug report. Process grading tells you it failed at step 4, by skipping the policy check.

Where it fails: expensive, often needs a model or a human to judge, and you can accidentally punish an agent for finding a smarter route than the one you imagined.

In plain words

A maths teacher marking a paper. Outcome: "the answer is 42, tick." Process: "show your working." Every good teacher uses both, because the student who wrote 42 with no working might be brilliant — or might have copied.

Now raise the stakes: a surgeon whose patient recovered. Outcome grading says "great surgeon." Process grading asks whether they washed their hands. You want both, and in a hospital you legally need the second.

The interesting part

The two disagree regularly, and the disagreements are the most valuable signal in your whole eval. A run that passes on outcome but fails on process is either a lucky guess or a policy violation you'd be sued for. A run that fails on outcome but passes on process usually means your tools are broken, not your agent. Most people build only one, so they never see this.

1.6 Three families of grader

The second three-ways choice, and the most practically important. Every time you sit down to score something, you are picking one of these.

GraderHow it worksCost & speedUse it when
Programmatic Plain code. Exact match, regex, JSON schema validation, running unit tests, or comparing final database state against expected state. Free, milliseconds, perfectly repeatable. There's a definable right answer. Always try this first.
Model-based
(LLM-as-judge)		 Give another LLM the output, a rubric, often a reference answer, and ask it to score. Cents per call, seconds, wobbles between runs. Quality is genuinely subjective — tone, helpfulness, writing quality — and code can't decide.
Human A person reads the output and scores it against a rubric. Expensive, slow, doesn't scale. Building your first 100 labelled examples, and checking your LLM judge agrees with you.

The single most common beginner mistake in this field: reaching for an LLM judge when a five-line programmatic check would have done the job. An LLM judge is a fallback for what code cannot decide, not a default.

In plain words

Marking a school exam. The multiple-choice section is marked by a machine reading the bubbles — instant, free, never wrong. The essay section needs a human examiner — slower, costlier, and two examiners will disagree a little.

No school would pay a human to mark the multiple-choice section. Teams do exactly that with LLM judges every day.

And the third row isn't optional. Humans aren't just a slow grader — they're the measuring stick you check the other graders against. A whole lesson goes to this later, because "how do you know your judge is right?" is a question most candidates can't answer.

1.7 Why evals rot

Three ways a perfectly good eval quietly stops being useful. Knowing these names makes you sound like someone who has done this before.

Contamination

The model was trained on your test data. It isn't reasoning; it's remembering. This is why public benchmark scores keep rising while real-world performance moves less — and it's the strongest argument for building your own tasks rather than downloading someone else's.

Saturation

Everything scores 97%. The eval can no longer tell good from great; all remaining signal is buried in noise. Time to write harder tasks.

Overfitting to the eval

You've tuned your prompt against the same 200 examples for six weeks. The number goes up; users notice nothing. You optimised for the test, not the job.

In plain words

All three are stories you know from school. Contamination is the exam paper leaking the night before. Saturation is an exam so easy everyone gets an A, so it can no longer decide who gets in. Overfitting is a coaching centre that drills last year's paper until students ace it and can't do anything else.

The habit that prevents all three

Keep a held-out slice — say 20% of your tasks that you never look at while iterating, and run only occasionally. If your main score climbs and the held-out score doesn't, you're overfitting. Extremely cheap insurance, and almost nobody bothers.

1.8 Vocabulary you now own

eval
A repeatable test suite for non-deterministic software.
golden set
The fixed collection of tasks you test against.
grader / scorer
The thing that turns an output into a score.
verifier
Same idea, RL vocabulary. Usually implies programmatic.
trajectory
The full recorded path of a run: messages, tool calls, results, in order.
verifiable reward
A score a machine can compute with no opinion involved.
offline eval
Fixed tasks, your machine, no real users.
online eval
Scoring live production traffic.
contamination
The model has already seen your test data in training.
saturation
Everyone scores near-perfect; the eval no longer discriminates.
held-out set
Tasks you deliberately don't look at while iterating.
cascading error
One early mistake making every later step look wrong.

1.9 Could you answer these out loud?

"What's outcome-based grading?"
Judging only the end result — usually the final state of the world — and ignoring the path. Used wherever correctness is machine-checkable: code tests passing, database state, the right numeric answer. Cheap and objective, but blind to luck and to policy violations along the way.
"Why not just use an LLM judge for everything?"
It costs money, varies between runs, and has known biases. Programmatic checks are free, instant and perfectly repeatable — so a judge should only cover what code genuinely cannot decide, like tone or writing quality.
"Your agent failed a task. First move?"
Open the trajectory and find the first step that went wrong, not the last — errors cascade, so the visible failure is usually downstream of the real cause.
"Your eval score has climbed for a month. Happy?"
Not yet. I'd check the held-out slice. A main score rising while the held-out score stays flat means I've been tuning to the test set, not improving the product.

1.10 What we'll use in the project — and why

Our project is a simulated support-operations backend: a seeded database of customers, orders and tickets, exposed to an agent as a handful of tools. The agent gets tasks like "customer 4471 says the replacement never arrived — make it right within policy."

Decisions locked in from this lesson
  • Offline eval as home base. It's the one that runs in CI, the one we control, and where the engineering skill lives. No online eval until much later.
  • Trajectory-level, not unit-level. The whole point is the thing RAG metrics can't see: a multi-step run with tools and state.
  • Outcome-based grading as the primary signal — compare final database state to expected state. This is exactly why we build a simulated world instead of downloading a dataset: we define what correct means, so a machine can check it with no opinion.
  • Process-based grading as a second, parallel score — policy assertions like "escalated before refunding over ₹5,000." Then we deliberately study where the two disagree, because that's where the interesting failures hide.
  • Programmatic graders only, to begin with. Zero LLM calls in the grading path — free to run, perfectly repeatable, and it forces us to learn the harder skill first. An LLM judge comes later for one narrow slice ("was the email to the customer appropriate?"), and then we calibrate it against your own human labels.
  • A held-out slice from day one. 20% of tasks we don't look at. Cheap habit, and a good line in the writeup.
