Memory and Context

Why a bigger context window does not fix forgetting, the four kinds of memory an agent needs, how the real systems build them — and how anyone honestly measures whether memory helped.

The #2 skill in the postings~40 minSources at the end

7.1 Context is a budget, not a container

The instinct everyone starts with: models have million-token context windows now, so memory is solved — just put everything in.

Anthropic's framing in their context-engineering guidance is the correction: treat the context window as a finite resource with diminishing marginal returns, and treat the job as curating the smallest set of high-signal tokens that maximises the chance of the outcome you want.

Two words matter there. Finite — obviously. And diminishing — which is the part people miss. Adding tokens does not merely stop helping at some point. It starts hurting, well before you reach the limit.

In plain words

A desk. A bigger desk lets you spread out more papers, and for a while that helps. Past a point the papers you need are buried under papers you don't, and you start working from whatever is nearest your hands. The desk got bigger; your ability to find things got worse.

Nobody solves a messy desk by buying a bigger desk.

The discipline of deciding what goes on the desk is context engineering. It is the successor to prompt engineering: prompt engineering asks what to write in one message; context engineering asks what the model should be holding at every step of a long task.

7.2 The evidence: context rot

This is not a matter of taste. It has been measured twice, three years apart.

Lost in the Middle (2023)

Liu et al. placed the same relevant document at different positions inside a long context and measured retrieval accuracy. Performance traced a U-shape: strong when the answer sat near the beginning or the end, notably worse when it sat in the middle. The effect held across six model families including GPT-3.5-Turbo, GPT-4 and Claude, with drops of tens of points in the worst positions.

Read that again, because it is stranger than it sounds. The information was in the context. The model could not use it, because of where it was.

Context Rot (2025)

Chroma's follow-up tested eighteen models across many input lengths and found degradation at every increment, not only near the limit — including on tasks so simple they were almost trivial. A model advertising a million-token window was already degrading at a small fraction of it.

The sentence to remember

Advertised context length is a capacity, not a competence. "It fits in the window" and "the model can use it reliably" are different claims, and only the first one is on the spec sheet.

This is also why Lesson 5's finding — that pruned contexts can outperform full history, not merely cost less — is not a paradox. Removing stale tokens removes distractors.

In plain words

Handing someone a 400-page report and asking about one sentence on page 190. They'll do well if it's in the summary or the conclusion. Buried in chapter seven, they skim past it — not because they can't read, but because attention is finite and the middle is where attention goes to die.

7.3 Four kinds of memory

"Memory" is doing too much work as a word. The taxonomy most frameworks now share comes from CoALA (Cognitive Architectures for Language Agents); Letta, Mem0 and LangChain all build on it. Four types, and they behave completely differently.

TypeHoldsLivesIn our agent
Working What's in play right now: the task, recent tool results, current state One run. Dies at the end. The message list. Already exists.
Episodic What happened, in sequence — past runs, decisions, outcomes Across runs "I shortlisted this role three weeks ago and heard nothing."
Semantic Facts about the world, abstracted from any one episode Across runs, indefinitely "Gradient Works is Series C, raised 20 months ago."
Procedural How to do things — skills, instructions, the agent's own playbook Across everything "Search per target title; one broad search truncates."

The distinction people blur most is episodic vs semantic, and it matters. Episodic is instance-specific with its context preserved: on 14 September, a search for "Forward Deployed Engineer" returned nothing. Semantic is the abstraction: this pipeline has no forward-deployed roles. One is a diary entry; the other is a fact distilled from many diary entries.

In plain words

A doctor. Working memory is the patient in front of them right now. Episodic is "this patient came in with the same complaint last March". Semantic is "this drug interacts badly with that one" — learned from many patients, attached to none of them. Procedural is how they run an examination, which improved over twenty years without them ever writing it down.

Lose any one of the four and you get a recognisably broken doctor.

Procedural memory is the one worth noticing, because it is newest and most interesting. LangChain's LangMem implements it as a prompt optimiser: the agent updates its own instructions based on how previous runs went. The prompt stops being a fixed artefact and becomes something the agent edits.

7.4 Three operations, and when to run them

Every memory system does three things: write, update, retrieve. The design decision that actually matters is when the writing happens.

Hot path

The agent writes memories during the run, as part of its work. Immediate, and the agent controls what is worth keeping. Cost: latency on every run, and the model spending attention on bookkeeping instead of the task.

Background

A separate process reads finished conversations and extracts memories afterwards. No latency cost to the user, and it can afford to be thorough. Cost: complexity, plus a window in which something learned is not yet available.

In plain words

Taking notes during the meeting versus writing the minutes after. Notes during keep you honest but slow the meeting. Minutes after are better written and arrive too late to help anyone still in the room.

Serious systems do both: rough notes in the moment, proper consolidation later. Which is also, roughly, what sleep is for.

And retrieval is where most memory systems quietly fail. Storing is easy. Deciding which three memories out of four thousand belong in this turn's context is the same hard problem as retrieval in RAG — which is why memory and retrieval are one discipline wearing two names.

7.5 The context ladder

Before reaching for a memory system, work down this list. Each rung is cheaper and safer than the one below it, and most teams jump straight to the bottom.

  1. Don't create the problem. Bounded tool returns, pagination, pre-computed fields, explicit truncation counts. Lesson 4. Free, and it removes most of the pressure.
  2. Tool result clearing. Drop the bodies of old tool results, keep the record that the call happened. Anthropic describes this as one of the safest lightweight forms of compaction, and it now ships as a platform feature rather than something you hand-roll.
  3. Compaction. Summarise the conversation so far and continue from the summary. Powerful and lossy — you are deciding, irreversibly, what mattered.
  4. Structured note-taking. The agent writes notes to a file outside the context and pulls them back when needed. Anthropic calls this agentic memory and highlights it as persistence with minimal overhead. Closer to a notebook than a database.
  5. An external memory store. A real system with write, update, retrieve and forgetting. Everything below this line is a component you now own and must evaluate.
Why the order matters

Compaction is a one-way door. Once the transcript is a summary, whatever the summariser dropped is gone and no later step recovers it.

Anthropic's managed-agent design avoids exactly this: the session log lives outside the context window and the agent interrogates it on demand via getEvents(), so it never has to make an irreversible decision about what to keep. Keeping the raw record and retrieving from it beats summarising it away.

Zep's temporal-graph approach has measured better than flat extraction on reasoning that depends on when something was true — a reported 63.8% against 49.0% on LongMemEval, roughly a fifteen-point gap, in a comparison run on the same setup.

How to read vendor benchmark numbers — the interview-grade point

Those same two vendors now publish figures around 92.5% and 94.7%. Those numbers are not comparable to each other: different underlying models, different evaluation setups, each measured by the vendor selling the thing.

Everything from Lesson 3 applies. A score without the model, the dataset version and the harness beside it is marketing, not measurement. When someone quotes a memory benchmark at you, the correct question is "against which model, on which split, scored by whom?"

7.8 How memory is measured

Three benchmarks are the standard vocabulary.

  • LoCoMo — very long multi-session conversations; can the agent answer questions spanning them?
  • LongMemEval — long-term memory across sessions, with categories for information extraction, multi-session reasoning, temporal reasoning and knowledge updates. The temporal and update categories are where flat storage falls over.
  • BEAM — the newer entrant, aimed at the same space.

The category that matters most in production is knowledge updates: she was targeting frontend roles, she is now targeting applied AI. A memory system that stores both facts and retrieves the stale one is worse than no memory, because the agent now acts confidently on something false.

The measurement that actually matters for you

Public benchmarks tell you whether a system is credible. They cannot tell you whether memory helps your agent on your tasks.

That answer comes from the thing you already built: run your suite with memory and without, same tasks, same seeds, and report the difference with its variance. That A/B is exactly what Wispr Flow's posting means by "enhance how context, instructions, skills, and memory are delivered to agents while measuring performance improvements."

7.9 Forgetting is a feature

Every memory system is eventually judged on what it throws away. Four mechanisms:

  • Staleness / TTL. Facts have shelf lives. Funding stage is good for months; "currently interviewing at X" is good for weeks.
  • Contradiction resolution. When a new fact conflicts with an old one, something must decide. Newest-wins is the usual default and is wrong often enough to matter.
  • Provenance. Every memory should carry where it came from and when. Without it you cannot audit a bad decision backwards — and Anthropic shipping per-write audit logs is a signal about where this is heading.
  • Decay by usefulness. Memories never retrieved are noise paying rent.
In plain words

A colleague who remembers everything you ever told them, including the bit you corrected six months ago, and cannot tell which version came later. That is not a good memory. That is a liability with a filing cabinet.

7.10 How memory systems fail

FailureWhat it looks likeDefence
Stale retrievalActs on a fact that was true last monthTTL, timestamps on every memory, temporal retrieval
Memory poisoningSomething false gets written, then treated as fact foreverProvenance, confidence, never writing from untrusted content unchecked
BloatThousands of memories, retrieval precision collapsesConsolidation, decay, retrieval limits
Wrong retrievalStores the right thing, fetches the wrong threeThis is a retrieval problem. Evaluate it as one.
Lossy compactionThe summariser dropped the one line that matteredKeep the raw log, retrieve from it, summarise last
Silent divergenceTwo runs behave differently and nobody knows whyMemory is state: version it, log writes, keep runs replayable
The one that will bite your evals

Memory breaks determinism. Lesson 2's whole argument was a world that behaves identically every run — and memory is, by design, state that persists between runs. Run the same task twice and the second run differs, because the first one happened.

So memory must be part of the seeded world, resettable by reset() like everything else. An eval suite that leaks memory between tasks is measuring an accident.

7.12 Interview answers, out loud

"Context windows are huge now. Isn't memory solved?"
No — capacity isn't competence. Liu et al. showed a U-shaped curve where information in the middle of a long context gets used far worse than the same information at either end, across six model families. Chroma's follow-up found degradation at every input-length increment, not just near the limit. So the discipline is curating the smallest high-signal context, not filling the biggest one.
"What kinds of memory does an agent need?"
Four, and CoALA is the shared vocabulary. Working memory is the current run. Episodic is what happened and when, context preserved. Semantic is facts abstracted from episodes. Procedural is how to do things — and that one is interesting because systems like LangMem implement it as the agent rewriting its own instructions based on how past runs went. They fail differently, so they need storing and retrieving differently.
"Would you use compaction?"
Last, not first. I'd go bounded tool returns, then tool-result clearing, then structured notes outside the window, and only then compaction — because compaction is a one-way door: whatever the summariser dropped is unrecoverable. Anthropic's managed-agent design makes that point by keeping the session log outside the context and letting the agent query it on demand, so it never has to decide irreversibly what to keep.
"A vendor says their memory system scores 94% on LoCoMo. Thoughts?"
I'd ask which model, which split, and who ran the harness — those figures are usually self-reported on different setups, so two vendors' headline numbers aren't comparable to each other. An earlier like-for-like comparison put a temporal-graph system about fifteen points above flat extraction on LongMemEval, which is more informative than either headline. And none of it tells me whether memory helps my agent, which is an A/B on my own suite.
"How would you evaluate memory?"
Same agent, same task suite, same seeds, with memory and without, several runs each, and report the delta with its variance. Then break it down by category — especially knowledge updates, where a stale fact retrieved confidently is worse than no memory at all. And I'd make memory part of the seeded world so it resets between tasks, otherwise the suite measures leakage rather than capability.
"What's the most dangerous memory failure?"
Poisoning. Something false — or something planted in untrusted tool output — gets written once and is then treated as established fact in every future run. Because it arrives as memory rather than as input, nothing downstream questions it. Defences are provenance on every write, confidence levels, and never writing to memory straight from untrusted content.

7.13 What we build

We already have the evidence for what is needed, from a run of our own that passed every check: the agent looked up the same company twice, ran four searches that returned nothing and learned nothing from them, and spent twenty-one steps making five decisions.

Decisions for our memory module
  • Start at rung one, not rung five. Our tool returns are already bounded with truncation counts. The next cheapest win is a within-run cache so get_company is never called twice for the same company.
  • Semantic memory first, because it is the clearest win: company facts with a TTL. Funding does not change in four steps and barely changes in twelve months.
  • Then episodic — which roles were shortlisted before and what came of them. That is the memory that makes the product genuinely useful to you daily.
  • Procedural is a stretch goal. "This pipeline has no forward-deployed roles" is a real learned procedure, and it would remove four wasted steps per run.
  • Memory lives in the seeded world and resets with it. Non-negotiable, or every eval number after this point is noise.
  • Every memory carries provenance and a timestamp from the first row written. Retrofitting provenance is the same trap as retrofitting prompt versions.
  • The deliverable is the A/B, not the feature. Same suite, same seeds, with and without, reported with variance. That number is the module.
