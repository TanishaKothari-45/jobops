Lesson 09 · Agent Env Lab

Cost, Latency and Routing

Where an agent's money and time actually go, the levers that move them in order of cheapness, and how to route work between models without simply making errors cheaper to produce.

~35 minSources at the end

9.1 Three currencies, and you cannot max all three

Every agent decision trades between quality, cost and latency. Most engineering conversations go wrong because someone optimises one and never says which of the other two they spent.

"It's 3% more accurate" is half a sentence. The full one is "3% more accurate, at 2.4× the cost and 900ms more latency" — and only that version is a decision a team can actually make.

In plain words

Shipping a parcel. Fast, cheap, reliable — pick two, and the courier makes you say which. Nobody finds that controversial. Agent engineering is the same trade, except the industry mostly quotes one number and hopes nobody asks about the others.

So the discipline here is not "make it cheap". It is make the trade explicit, then measure it.

9.2 Where the money actually goes

Four facts that reshape most people's intuition.

1 · Input and output are priced differently

Output tokens typically cost several times what input tokens cost. But agents are input-heavy: the system prompt, every tool schema and the entire accumulated conversation are re-sent on every turn. A twenty-step run re-sends the same tool definitions twenty times.

2 · Tool results dominate the input

From Lesson 5: roughly 84% of a typical agent's context is observation tokens — tool output, accumulating. You are paying to re-send search results the agent already read, on every later turn.

3 · Cost is quadratic in steps, not linear

The one people get wrong. Each step appends its output to the history, and the whole history is re-sent next step. Twenty steps is not twice the cost of ten — it is nearer four times, because you pay for a growing context repeatedly.

In plain words

Re-reading the entire meeting transcript aloud before anyone says a new sentence. The tenth sentence costs ten readings. The twentieth costs twenty. A meeting that runs twice as long does not cost twice as much.

4 · Retries and failures are pure loss

A malformed tool call that gets retried costs a full round trip and produces nothing. A run that hits its step limit and fails costs everything it spent. Neither appears in "cost per call", which is exactly why that metric misleads — §9.7.

9.3 The cost levers, cheapest first

Work down this list. The first three are close to free, and most teams skip to the fourth.

1 · Don't send it in the first place

Bounded tool returns, pagination, pre-computed fields, truncation counts — Lesson 4. A tool returning 8 rows with a count instead of 34 with full descriptions is the single largest cost lever available, and it improves quality at the same time by reducing context rot.

2 · Prompt caching

The stable prefix of your prompt — system prompt, tool schemas, long documents — is cached and re-read at a steep discount rather than reprocessed.

90%discount on cached input reads — cached tokens at 10% of the standard rate
25%one-time write premium to place the prefix in the cache
85%latency reduction reported on cached prompts
11.5s → 2.4sthe published example: summarising a 100K-token book

For an agent this is close to free money, because the expensive stable part — system prompt plus twelve tool schemas — is identical on every turn of every run. That is the ideal cache shape.

The catch: it caches a prefix. Anything that changes near the front invalidates everything after it. Put stable content first and volatile content last — a timestamp injected into your system prompt can silently cost you the entire cache, with no error anywhere.

3 · Batch processing

Work nobody is waiting on — running an eval suite, nightly enrichment, bulk classification — goes through a batch API at roughly 50% off, typically returning within 24 hours. Both major providers offer it.

And the discounts stack: batch plus cached reads reaches around 95% savings on the repeated portion. Your eval suite is precisely this workload.

4 · Use a smaller model

Before building a router, check whether the small model simply does the job — measured on your own suite, not assumed. This is the step people skip on the way to something more interesting.

9.4 Where the time actually goes

Latency in an agent is not one number. It decomposes, and the decomposition tells you what to fix.

  • Time to first token (TTFT) — how long before anything appears. This is what a user experiences as "is it working?"
  • Generation time — tokens per second × output length. Shorter outputs are faster outputs.
  • Tool execution — your own code, your own databases, your own APIs. Often the largest slice, and the one people forget is theirs to fix.
  • Round trips — the multiplier. A twenty-step run pays all of the above twenty times, in series.
The step count is the latency budget

If one turn takes 3 seconds, a 20-step run takes a minute. No amount of model-level optimisation fixes that. The fix is fewer steps.

Which reframes something from Lesson 4: better tool design is a latency intervention. A tool returning pre-computed fields removes a step. A tool that answers in one call instead of three removes two.

Latency levers

  • Stream. Does not reduce total time; transforms the experience of it. TTFT is the number users feel.
  • Parallelise reads. Three independent lookups in parallel cost one lookup of wall-clock time. Never parallelise writes (Lesson 8).
  • Cache. The same 85% that saves money saves time.
  • Fewer, fatter tools. Every round trip removed is a whole turn of latency.
  • Smaller models for easy steps. Often several times faster, not merely cheaper.
  • Speculative prefetch. Start the likely next tool call while the model is still generating. Powerful, and it wastes work when you guess wrong.

9.5 Routing: three designs

Routing means using a cheap model where it suffices and an expensive one where it does not. The savings are real and well documented, and the three designs fail differently.

DesignHow it decidesCostFails when
Predictive router A classifier reads the request before any model call and picks a tier Adds roughly 300–500ms to every request It is confidently wrong on exactly the hard edge cases that most needed the strong model
Cascade / escalation Cheap model answers first; escalate if the answer fails a check Double latency and double cost on whatever escalates The check is weak — then you pay twice and still ship the wrong answer
Semantic router Embed the query, route by similarity to reference prompts per tier One embedding call, no model call Novel phrasings fall outside every reference cluster

What the research says

RouteLLM reported roughly an 85% cost reduction on MT-Bench while retaining about 95% of GPT-4's quality, and the wider literature puts routing savings in the 40–85% range depending on workload. The strongest routers are learned, and the most effective training signal is preference data — pairs of responses labelled by which was better.

The finding that should change your design

LLM self-reported confidence is poorly calibrated. A model will produce a fluent, authoritative answer with high token probabilities while being factually wrong.

So a cascade gated on "the model said it wasn't sure" escalates the wrong requests. The gate has to be external: a schema validation failure, a checkable fact that did not check out, a verifier's verdict, a known-hard task type.

Put plainly: routing is only safe if something independent checks the cheap answer. Otherwise you have not saved money — you have made errors cheaper to produce, which is worse than expensive correctness.

In plain words

A junior handling the easy tickets. That works if someone reviews the hard ones they misjudged as easy. Without review you have not built a triage system — you have built a system that gets the difficult cases wrong, faster and cheaper than before.

9.6 Caching, properly

Three distinct things share the word, and confusing them causes real bugs.

KindCachesHits whenRisk
Prompt cacheThe provider's processing of a stable prefixThe prefix is byte-identicalAny change near the front invalidates everything after it
Exact-match cacheWhole responses, keyed on the exact requestIdentical input seen beforeStaleness — the world moved and your answer did not
Semantic cacheResponses keyed on embedding similarityA similar question was askedFalse hits: "similar" is not "same", and the difference may be the whole question

Semantic caching is the one to be careful with. "What's my refund status?" and "What's my refund policy?" embed closely and have completely different answers. If you use it: set the similarity threshold high, exclude anything user-specific, and measure the false-hit rate rather than assuming it is small.

9.7 The metric that changes the conversation

Cost per successful task, not cost per call

A cheap model that answers, fails verification and escalates costs more than going straight to the strong model — two calls instead of one, plus the verification. Per-call cost records this as a saving. Per-successful-task records it as the loss it is.

The same correction applies to latency (time to a correct answer, including retries and escalations) and to every optimisation you will ever be asked to justify. Measured per successful outcome is the only framing in which the three currencies trade honestly.

Things a per-call view hides entirely:

  • Retries after malformed output
  • Runs that hit the step limit and produced nothing
  • Escalations from a cheap tier that did not work
  • Human time spent fixing a wrong answer — usually the largest cost in the system, and almost never counted

9.8 Measuring it

Percentiles, not averages

Report p50, p95 and p99. An average hides the tail completely, and the tail is what users remember and what pages your on-call. A system with a 2-second average and a 40-second p99 has a serious problem that the average denies.

In plain words

"The average wait here is twenty minutes" tells you nothing about whether one patient in twenty waits six hours. The average is the number on the brochure; the p99 is the number in the complaint.

Attribute per span

Record tokens, cost and duration per step, not per run. A run that cost ₹40 tells you nothing actionable. A run where one fetch_posting call accounted for 60% of the tokens tells you exactly what to fix.

Track the shape, not only the total

  • Steps per run — the strongest single predictor of both cost and latency
  • Cache hit rate — a sudden fall usually means a prompt change near the prefix
  • Escalation rate — if most requests escalate, your routing is a tax
  • Retry rate — pure waste, and usually fixable in the tool layer
  • Cost per successful task over time — the one number for a dashboard

9.9 How optimisation goes wrong

MistakeWhat happens
Optimising before measuringYou speed up the 5% and leave the 60% untouched. Profile the trace first.
Routing without verificationErrors become cheaper to produce. The worst outcome on this list.
Cache killed by a timestampA dynamic value near the prefix silently costs every cache hit, with no error.
Semantic cache false hitsA confidently wrong answer to a question nobody asked.
Optimising the averagep50 improves, p99 worsens, users are angrier than before.
Cutting quality invisiblyCost halves and nobody notices the score fell, because nobody ran the suite.
The rule that prevents the last one

Every cost or latency change is re-run against the eval suite before it ships. An optimisation that cannot show its quality delta is not an optimisation — it is a bet, and the entire point of building the suite was to stop betting.

9.11 Interview answers, out loud

"Your agent costs too much. What do you do first?"
Measure before touching anything — tokens per step, not per run, because the culprit is usually one tool returning far too much. Then in order: bound the tool returns, turn on prompt caching for the stable prefix, move anything asynchronous to batch. Those three are close to free. Only then smaller models or routing, which add real complexity. And cost is roughly quadratic in steps, so cutting step count usually beats everything else.
"How does model routing work, and when does it hurt?"
Cheap model first, escalate on a signal. The literature puts savings around 40–85% — RouteLLM reported about 85% cost reduction while holding roughly 95% of GPT-4's quality. It hurts when the escalation gate is the model's own confidence, because self-reported confidence is poorly calibrated: models are fluent and authoritative while wrong. The gate has to be external — schema validation, a verifier, a checkable fact. Routing is only safe if something independent checks the cheap answer; otherwise you have just made errors cheaper to produce.
"Why is prompt caching such a big deal for agents specifically?"
Because the expensive stable part — system prompt plus every tool schema — is identical on every turn of every run, which is the ideal cache shape. Cached reads run about 90% cheaper with a 25% write premium, and up to 85% faster. The catch is that it caches a prefix, so anything volatile near the front invalidates the rest — a timestamp in the system prompt can cost you the whole cache without any error appearing anywhere.
"Your p50 latency is 2 seconds. Good?"
I don't know yet — tell me the p95 and p99. Averages and medians hide the tail, and the tail is what users remember and what wakes on-call. For an agent I'd want steps per run alongside it, because if one turn is 2 seconds then a 20-step run is 40, and no model-level optimisation fixes that. Fewer steps does.
"How do you know an optimisation didn't hurt quality?"
Re-run the eval suite, paired on the same tasks and seeds, and report the delta with its variance. An optimisation that can't show its quality delta isn't an optimisation, it's a bet. And I'd report cost per successful task rather than per call, because a cheap model that fails and escalates costs more than going straight to the strong one — per-call cost records that as a saving.

9.12 What this means for our project

Decisions
  • We already pulled lever one. Bounded returns, truncation counts and pre-computed fields were tool-design choices — they are also the biggest cost lever, taken before we knew it.
  • Record tokens and duration per step from the very first LLM run. The trajectory already has fields for both; populating them later makes every earlier run unattributable.
  • Structure the prompt for caching — system prompt and tool schemas first, task and history after. Free, and impossible to retrofit without invalidating past measurements.
  • The eval suite runs on batch where latency does not matter. Half price for work nobody is waiting on.
  • No routing until there is a verifier. We have graders, which is exactly the external check routing requires — so the escalation gate must be a grader verdict, never the model's own confidence.
  • Report cost per successful task in the dashboard, beside p95 and score. Three numbers, one screen.
