Lesson 11 · Agent Env Lab

Reliability and Observability

What keeps an agent working when things fail, and what lets you see why when they do. The two subjects are one subject: you cannot make reliable what you cannot observe.

~40 minSources at the end

11.1 The gap between a demo and a product

A demo runs once, on a good network, with a cooperative model, while someone watches. A product runs ten thousand times, at 3am, while an API is rate-limiting, a database is failing over, and nobody is looking.

Almost everything in this lesson exists to handle the second case. And the reason it is one lesson rather than two is that the halves depend on each other: you cannot make reliable what you cannot observe, and observability over an unreliable system just produces more detailed reports of the same mystery.

In plain words

A restaurant that cooks one perfect dish for a critic is not a restaurant. A restaurant is what happens on a Saturday when the fridge breaks, two staff call in sick and forty covers arrive at once. Nobody judges a kitchen by its best night.

Part one · Reliability

11.2 Transient or terminal: the classification everything rests on

Every failure is one of two kinds, and confusing them causes both of the classic mistakes.

TransientTerminal
ExamplesTimeout, 503, rate limit, connection reset, database failoverInvalid arguments, record does not exist, permission denied, malformed output
Will retrying help?Yes — the world changesNo — the same call fails identically forever
Who handles itYour code, automaticallyThe agent — hand it the error and let it adapt

This is Lesson 5's rule stated precisely: retry the transport, not the judgement. Auto-retrying a validation error burns money to fail identically. Handing a network blip to the model wastes a reasoning step on something it cannot fix.

The third category people forget

Ambiguous failures. A request timed out — did the server process it or not? You genuinely do not know. Treat it as transient and retry, and you risk doing the work twice; treat it as terminal, and you risk not doing it at all.

There is no way to resolve this from outside, which is exactly why the next section exists. Idempotency is not a nice-to-have — it is the only honest answer to a timeout.

11.3 Idempotency

An operation is idempotent when doing it twice has the same effect as doing it once. Reads are naturally idempotent. Writes are not, and that is the whole problem.

The standard mechanism: the caller generates a key, the server records it, and a second call with the same key returns the first result instead of repeating the work.

send_message(draft_id="msg_0003",
             idempotency_key="run_8821:step_14:send")

# first call   -> sends, stores the key, returns {sent: true}
# second call  -> key seen, returns the SAME result, sends nothing

Three properties the key must have:

  • Deterministic from the intent, not random. Derived from the run and the step, so a resumed run generates the same key rather than a new one. A random key defeats the entire mechanism while looking like it works.
  • Stored with the result, so a repeat returns what the first call returned.
  • Retained longer than your retry window — and longer than any plausible crash-recovery gap.
In plain words

A cheque number. Hand the bank the same cheque twice and they pay once, because the number is on it and they have seen it. Not because the teller was attentive — because the system was designed so attention is not required.

The design rule

Make every write idempotent before you add retries. Retries on non-idempotent writes do not improve reliability; they convert an occasional failure into an occasional double-charge, which is strictly worse.

11.4 Retries, done properly

Naive retries are worse than none, because they arrive all at once at the moment a system is least able to cope.

Exponential backoff

Wait 1s, then 2s, then 4s, then 8s. Gives a struggling dependency room to recover instead of hammering it.

Jitter — the part people omit

If a thousand clients all fail at the same instant and all back off by exactly 1s, they all retry at the same instant. You have rebuilt the stampede one second later. Jitter randomises each delay, spreading the retries out.

In plain words

A power cut. If every fridge and heater in the city restarts the instant power returns, the grid trips again. Utilities stagger reconnection on purpose. Jitter is the same idea, and skipping it is how a short outage becomes a long one.

A retry budget

Cap retries globally, not only per call. Three attempts each across twelve steps is thirty-six potential calls from one run. Budget the run, or a bad afternoon becomes a bill.

Never retry

  • A non-idempotent write without an idempotency key. Charging a card twice is not a transient error; it is a legal problem.
  • A validation failure — identical input, identical rejection.
  • Anything a human has already been told failed. Two apologies for one problem is its own incident.

11.5 Timeouts, circuit breakers, bulkheads

Three patterns that stop one slow dependency taking down everything.

Timeouts

Every external call gets one. A call without a timeout can hang forever, and in an agent that means a run holding resources indefinitely while producing nothing. Set them per dependency: a database in milliseconds, a model call in seconds, a browser fetch in tens of seconds.

Circuit breakers

After N consecutive failures, stop calling the dependency at all for a cooling-off period, then let one probe through. If it succeeds, resume.

The point is not to protect you from the dependency — it is to stop you making the outage worse, and to fail fast so the agent can degrade rather than wait.

In plain words

An electrical circuit breaker does not fix the fault. It trips so the fault does not burn the house down, and it lets you test the line once you think it is fixed. Software borrowed both the name and the logic.

Bulkheads

Separate resource pools per dependency, so a slow search API cannot exhaust the connections the payments API needs. Named after ship compartments: one floods, the vessel stays up.

11.6 Durable execution

The problem in one sentence: a twelve-step agent run in a single process, interrupted at step seven by a deploy, a crash or a rate limit, starts again from step one — repeating every side effect it already performed.

Durable execution persists state at every step, so an interrupted run resumes from the last completed checkpoint rather than the beginning. It is the defining property of workflow engines, and several — Temporal, Restate, Inngest, Azure Durable Task, AWS Step Functions — now position these primitives explicitly for agents.

What has to be persisted

  • The message history so far
  • Which steps completed, and what each returned
  • Idempotency keys already issued
  • The step count and any budget consumed
Resume is only safe with idempotency

Crash recovery re-executes the boundary step, because you cannot know whether it completed. Without idempotency keys, every resume risks repeating the last action — and the last action is disproportionately likely to be a write, because writes are slow and slow things are where crashes land.

So the order is fixed: idempotency first, retries second, durable execution third. Built the other way round, each layer amplifies the previous one's bug.

Do you need a workflow engine?

Not always. For short runs, checkpointing to your own database at each step is often enough and much simpler. Reach for an engine when you have work measured in hours or days, human-in-the-loop waits, complex compensation logic, or a need to replay history exactly. The honest position is that the property matters and the engine is an implementation choice.

11.7 "Exactly-once" is a lie

Distributed systems cannot guarantee exactly-once delivery. What they offer is at-least-once delivery, and what you build on top is idempotent handling — and the combination behaves as exactly-once from outside.

The sentence

"Exactly-once delivery isn't available. At-least-once delivery plus idempotent handlers gives you exactly-once effects, which is what anyone actually wanted."

The same reasoning disposes of the ambiguous timeout from §11.2. You never learn whether the first call landed. You stop needing to know.

11.8 Degrading instead of dying

When something is unavailable, the choice is not fail or succeed. It is what smaller thing can we still do?

BrokenBad responseDegraded response
Enrichment API downFail the runProceed without that field; mark the output incomplete
Primary model rate-limitedFail the runFall back to another model; record which one answered
Search returns nothingInvent an answerAbstain, and say what was searched
Approval queue stalledAct without approvalQueue the action and report it as pending

Note the last row. Degradation must never cross a safety boundary. "The approval service was down so we proceeded" is not graceful degradation — it is a guardrail failing open, and a guardrail that fails open under load fails exactly when it was most needed.

And whenever you degrade, say so in the output. A silently degraded answer is indistinguishable from a good one, which means nobody ever learns the dependency was down.

Part two · Observability

11.9 Why agents are harder to observe

Ordinary software fails deterministically and leaves a stack trace. Agents do neither.

  • No stack trace. The "bug" is a decision, and decisions do not raise exceptions. Nothing threw; it simply chose wrongly.
  • Non-deterministic. The same input produces a different path, so "just reproduce it" is not straightforwardly available.
  • Failures are semantic, not structural. Every call returned 200. The answer is still wrong.
  • The unit of debugging is the trajectory, not the line — and errors cascade, so the visible failure is usually downstream of the real one.

Which is why the trace is not a debugging aid for agents. It is the primary artefact, and it has to be designed rather than collected as an afterthought.

11.10 The standard: OpenTelemetry GenAI conventions

Until recently every vendor invented its own trace format. That has converged: OpenTelemetry's GenAI Special Interest Group, formed in April 2024 under the Semantic Conventions SIG and backed by the CNCF, defines a standard schema for AI telemetry — and the major observability vendors now support it natively.

The span tree

invoke_agent                      # the whole run
├── chat                          # one LLM call
├── execute_tool  search_postings # one tool call
├── chat
├── execute_tool  get_company
└── chat

The attributes

Names worth knowing, because using the standard ones means any compatible backend understands your traces with no custom work:

AttributeCarries
gen_ai.operation.nameWhat this span is — chat, execute_tool, invoke_agent
gen_ai.request.modelWhich model was asked
gen_ai.provider.nameWhich provider — so results compare across vendors
gen_ai.usage.input_tokensInput tokens for this call
gen_ai.usage.output_tokensOutput tokens for this call
gen_ai.response.finish_reasonsWhy generation stopped — stop, tool_calls, length

The scope has since expanded across agent orchestration, MCP tool calling, content capture and quality evaluation. As of early 2026 most of these conventions remain experimental — worth saying out loud, because names can still change and your instrumentation should sit behind a thin layer.

Why this matters more than it sounds

Adopting the standard names is what stops your observability being locked to one vendor. Span attributes are the schema of your operational data, and inventing your own is the same category of decision as inventing your own date format.

11.11 What a good span carries

  • One trace id across the whole run, and across every agent in a multi-agent system — otherwise attribution collapses (Lesson 8).
  • Tokens and duration per span, not per run. A run costing ₹40 is not actionable; one tool call accounting for 60% of the tokens is.
  • Versions: model, prompt version, tool-schema version, dataset version. A trace you cannot attribute to a configuration is a story without a date.
  • The stop reason, always — "finished" and "hit the step limit" look identical otherwise.
  • Inputs and outputs, sampled. Full content on every span is expensive and a privacy exposure; sample it, and redact before it leaves your process.
  • Errors with their classification — transient or terminal, retried or not. This makes retry behaviour auditable rather than folklore.
Content capture is a privacy decision, not a logging decision

Prompts and completions contain whatever your users typed. Capturing them wholesale means your observability backend is now a system holding personal data, with everything that implies for retention and access.

Default to capturing structure — which tools, how many tokens, what finish reason — and sample content deliberately, redacted. "We log everything" should be a decision someone made on purpose.

11.12 The numbers worth a dashboard

A dashboard nobody reads is a dashboard nobody built well. Three numbers, one screen:

  1. Quality — the eval score, or an online proxy for it
  2. Cost per successful task — not per call (Lesson 9)
  3. p95 latency — not the average

Then a second tier you consult when one of those moves: steps per run, tool error rate, retry rate, cache hit rate, escalation rate, abstention rate, and the distribution of stop reasons.

In plain words

A car dashboard shows speed, fuel and temperature — not every sensor in the engine. The diagnostics exist, and you read them when a light comes on. A dashboard with forty gauges is one nobody looks at, which is functionally the same as having none.

11.13 Online evaluation and drift

Offline evals tell you whether a change broke something you already knew about. They cannot tell you that the world moved. Three things change under you with no deploy on your side:

  • The model. Providers update them. Behaviour shifts without a line of your code changing.
  • The data. Users start asking different things than when you built the golden set.
  • The dependencies. An API changes a field; your parsing quietly degrades.

The practical pattern is the same two-tier shape as grading in Lesson 3: cheap programmatic checks on 100% of traffic — schema validity, tool error rate, abstention rate, step counts — plus an expensive judge on a small sample. Alert on the cheap signals; investigate with the expensive one.

And watch distributions, not only averages. A rise in steps per run, a fall in cache hit rate, or a change in the mix of stop reasons are early warnings, and they show up before quality scores do.

11.16 Interview answers, out loud

"How do you make an agent reliable?"
In a fixed order, because each layer depends on the one before. Idempotency on every write first — deterministic keys derived from the run and step, so a resume generates the same key. Then retries with exponential backoff and jitter, and a global budget, only on transient failures. Then durable execution, so a crash resumes from the last checkpoint instead of replaying every side effect. Built the other way round, each layer amplifies the previous one's bug.
"A tool call times out. Did it happen?"
You can't know, and that's the point. It's the ambiguous case — retry and you might do it twice, don't and you might not do it at all. The answer isn't better detection, it's idempotency: make the repeat harmless and stop needing to know. That's also why exactly-once delivery isn't something you can buy — at-least-once plus idempotent handlers gives you exactly-once effects, which is what anyone actually wanted.
"Why does jitter matter?"
Because without it, everyone who failed at the same moment retries at the same moment. A thousand clients backing off exactly one second rebuild the stampede one second later. Jitter spreads them. It's the same reason utilities stagger reconnection after a power cut — synchronised recovery is how a short outage becomes a long one.
"How do you debug an agent in production?"
From the trace, because there's no stack trace — the bug is a decision, and decisions don't raise exceptions. One trace id across the run, a span per LLM call and per tool call, tokens and duration on each, plus model and prompt versions so it's attributable. Then find the first wrong step, not the last, because errors cascade. And I'd use the OpenTelemetry gen_ai conventions rather than invent attribute names, so the traces aren't locked to one vendor.
"What would you put on the dashboard?"
Three things: quality score, cost per successful task, and p95 latency — not averages, because the tail is what users remember. Second tier when one of those moves: steps per run, tool error rate, retry rate, cache hit rate and the distribution of stop reasons. A dashboard with forty gauges is one nobody reads, which is the same as not having one.
"Your quality score dropped and nothing was deployed. What happened?"
Drift — three candidates. The provider updated the model. The traffic mix changed, so the golden set no longer represents what users ask. Or a dependency changed a field and parsing degraded quietly. I'd look at distributions first, because steps per run, tool error rate and stop-reason mix all move before the quality score does. That's what online eval is for: cheap checks on all traffic, an expensive judge on a sample.
"The approval service is down. Should the agent proceed?"
No. That's a guardrail failing open, and a guardrail that fails open under load fails precisely when it was most needed. Graceful degradation means a smaller correct answer — queue the action and report it as pending — never crossing a safety boundary. And whatever we degrade to, the output has to say so, or a degraded answer is indistinguishable from a good one.

11.17 What this means for our project

Decisions
  • Idempotency keys before anything else. Derived from run id and step index, so a resumed run produces the same key. Every write tool takes one.
  • Our tool errors already classify themselves. A broken tool returns "temporarily unavailable, continue without it if you can" — a transient failure told plainly. Terminal errors name the recovery path instead. That distinction is already in the text.
  • Checkpoint to Postgres per step, not a workflow engine. Runs are short; the property matters, and the engine is a choice we do not need yet.
  • Crash-and-resume is a demo, not just a feature. Kill the process mid-tool-call, resume, prove no duplicate action. Hard to fake, and it shows the whole stack working at once.
  • Instrument with the gen_ai conventions from the first traced run — standard names, behind a thin layer since they are still experimental.
  • The trajectory already has the fields. Tokens, timing, prompt version and stop reason are in the recorder; they need populating, and populating them later makes every earlier run unattributable.
  • Degradation never crosses the approval gate. If approval is unavailable the action queues — and that is a property the process grader should check.
