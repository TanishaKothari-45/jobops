Multi-Agent Systems

The field's two loudest voices disagree about this, both with evidence. The synthesis they have converged on is one sentence long — and it answers the "many agents, one dashboard" question directly.

8.1 The question is not "how many agents"

Teams reach for multiple agents for the wrong reason almost every time: the system feels big, so it seems like it should be split. That is org-chart thinking applied to software.

The real question is narrower and much more answerable: what does a handoff buy, and what does it cost? Everything below is an attempt to price those two things, because once you can price them the architecture decides itself.

In plain words

Adding people to a project. Sometimes it genuinely doubles the work done. Sometimes it means four people now have to agree on what they are doing, and everything slows while everyone writes status updates to each other.

You already know which is which in human teams. The same intuition applies, for the same reason: coordination is not free.

8.2 Two camps, both with evidence

This is unusually well documented for an architecture debate, because both sides published numbers.

Anthropic · Research system
Split it. The gain is large.
An orchestrator–worker design with parallel subagents beat single-agent Claude Opus 4 by 90.2% on their internal research eval.

The mechanism they identify: token usage alone explains about 80% of the variance in performance. Subagents work because each gets its own context window — you are buying more attention, not more intelligence.
Cognition · Devin
Don't. It fragments context.
Their position: multi-agent systems today are brittle, because splitting work splits context. Even when each subagent gets the full task description, none of them sees the others' intermediate decisions and assumptions.

Their prescription: default to single-threaded linear agents, and rule out multi-agent designs unless they clear a high bar.

Both are right, and they appear to disagree because they built different kinds of system.

The cost nobody quotes alongside the 90.2%

That same Anthropic system uses roughly 15× the tokens of a normal chat interaction.

So the honest sentence is not "multi-agent is better". It is: multi-agent bought a large quality gain for fifteen times the cost, on a task where breadth of search was the bottleneck. If your bottleneck is something else, you have bought the cost without the gain.

8.3 What a handoff actually costs

Four costs, and the first is the one people miss.

1 · Implicit decisions don't travel

This is Cognition's core point and it is subtle. When an agent does something, that action encodes a decision it never stated — it chose this reading of an ambiguous instruction, it assumed that format, it decided an edge case did not matter. Hand the task to a second agent and it receives the words, not the reasoning behind them. So it makes its own, different, unstated assumption.

Two agents, both behaving reasonably, producing work that does not fit together.

In plain words

Two developers given "build a login page", working in separate rooms, no communication. One builds the front end assuming email login. One builds the backend assuming phone number. Neither made a mistake. Neither wrote their assumption down. The system does not work.

2 · Context duplication

Every subagent needs enough background to do its job, so shared context gets copied into every window. That is where the 15× comes from.

3 · Attribution collapses

When a five-agent system produces a wrong answer, which agent was wrong? Debugging one trace is hard enough; debugging five interleaved ones — where the failure may live in the handoff rather than in any agent — is materially harder. This is the cost that hits in month three, not week one.

4 · Write conflicts

Two agents acting on the same record at the same time is a data-integrity bug you usually cannot reproduce. It also has the cleanest solution, which is section 8.5.

Notice that the two most reliable patterns — router and sequential chain — are barely multi-agent at all. You wrote the control flow; the models fill in the steps. That is a feature.

8.5 The synthesis: read wide, write narrow

Cognition's more recent position, after running these systems in production, sharpens into one sentence — the most useful thing in this lesson:

The line to remember

Multi-agent systems work best when writes stay single-threaded and the additional agents contribute intelligence rather than actions.

Unpack it. Parallel agents are excellent at gathering: searching, reading, analysing, proposing. Each fills its own context window with material, which is exactly the mechanism behind Anthropic's gain. Parallel agents are dangerous at acting: two writes racing on one record, two refunds issued, two emails sent.

So: fan out to read, funnel to write. Many agents may investigate; one path commits.

In plain words

A newsroom. Ten reporters chase ten leads in parallel — that is the whole point of having ten reporters. But one editor decides what goes to print. Nobody runs a paper where any reporter can publish directly, and it is not because reporters are untrustworthy.

Notice this is the same rule as parallelise reads, serialise writes from tool design, arrived at independently at a different layer. When a principle shows up twice from different directions, it is usually load-bearing.

8.6 What agents share, and what they must not

"Multiple agents on one dashboard" is really a question about shared state, and Lesson 7's memory taxonomy answers it cleanly — the rule differs per type.

MemoryShared?Why
WorkingNeverIt is one run's scratch state. Sharing it is how a billing agent's half-formed notes end up steering a support agent.
SemanticYesFacts about the customer. If two agents hold different facts they tell the same person different things — the exact failure a unified dashboard exists to prevent.
EpisodicRead-only"Billing already credited this customer yesterday" has to be visible, or two agents do the same thing twice. Readable by all, writable only by the agent whose episode it is.
ProceduralCarefullyShared playbooks drift and affect everyone at once. Version them and treat a change like a deploy.
The unified-dashboard trap

Putting several agents behind one interface makes them look like one system to the customer — so the customer now expects them to behave like one. They will notice immediately when the billing agent has not heard what the support agent promised.

The dashboard is therefore not a UI change. It is a commitment to shared semantic memory and visible episodic history. Skip that, and the unified interface actively makes the product worse than separate ones were, because it puts the inconsistency in one place.

8.7 When splitting genuinely helps

Five good reasons. If none applies, use one agent with better tools.

  1. Genuine parallelism over independent work. Ten sources to read, none depending on another. Anthropic's case, and where the gain is real.
  2. Different permissions. A read-only research agent and an agent that can move money should not be the same principal. This is a security boundary, and the strongest reason on the list.
  3. Different tools entirely. When one agent's tool list would otherwise reach forty and selection accuracy collapses.
  4. Different models. A cheap model for triage, an expensive one for the hard step — a routing decision that happens to look like multi-agent.
  5. Context isolation for safety. Keeping untrusted content inside a subagent that cannot act limits what a prompt injection can reach.

Notice how few are "the problem is big". Size is not a reason. Independence, permissions and blast radius are.

8.9 Evaluating one is harder

Everything from Lessons 1–3 still applies, plus three new problems.

  • Attribution. The end state tells you the system failed, not which agent failed. You need per-agent sub-scores, or you are debugging blind.
  • Handoffs are gradeable objects. Did agent A pass enough for B to succeed? That is a check, and almost nobody writes it — which is why "lost in the handoff" failures survive so long.
  • Variance compounds. Five non-deterministic components in series produce far more spread than one, and pass^k falls fast: if each agent is 90% reliable, five in a row are about 59%.

That last number is the argument against unnecessary splitting, stated arithmetically. Every agent you add multiplies in another probability below one.

8.11 Interview answers, out loud

"When would you use multiple agents?"
When there is genuine independent parallelism, when parts need different permissions, when one agent's tool list would grow large enough to hurt selection, or when I want untrusted content isolated in something that cannot act. Not because the problem is large — size is not a reason. I default to one agent with good tools, because every agent I add multiplies in another probability below one: five 90%-reliable steps in series is about 59%.
"Anthropic says multi-agent beat single-agent by 90%. Doesn't that settle it?"
It settles it for that task. The same system used about fifteen times the tokens, and their own analysis says token usage explains roughly 80% of the variance — so what the architecture bought was more context windows, on a task where breadth of search was the bottleneck. Cognition's counter-argument concerns a different bottleneck: splitting work splits context, and agents stop seeing each other's implicit decisions. Both are right about their own system.
"Multiple agents share one dashboard. How do you stop them contradicting each other?"
Split memory by type. Working memory is never shared — it is one run's scratch state. Semantic facts about the customer must be shared, or two agents tell the same person different things, which is exactly what a unified interface makes visible. Episodic history is shared read-only so nobody repeats what another already did. And the dashboard is not a UI change — it is a commitment to that shared state, because the customer now expects one system.
"Two agents might both issue a refund. How do you prevent it?"
Single-threaded writes. Many agents may investigate and propose; one path commits. Plus idempotency keys, so even a retry does the work once. It is the same rule as parallelise-reads-serialise-writes at the tool layer, which is a decent sign it is load-bearing rather than a preference.
"How do you debug a five-agent system?"
One trace id across every agent, per-agent sub-scores so attribution does not collapse, and I would grade the handoffs themselves — did A pass enough for B to succeed? Almost nobody writes that check, which is why "lost in the handoff" failures survive so long. And more runs than you would expect, because variance compounds across the chain.

8.12 Applied to the dashboard problem

How to answer "make these agents work well together"
  • Do not merge them into one agent, and do not let them act independently either. Keep them separate for permissions and tool-set reasons, and put one commit path in front of every write.
  • Shared semantic memory about the customer, or the unified interface makes the product worse than separate ones were, because now the inconsistency is visible in one place.
  • Episodic history readable by all, so no agent repeats an action another already took. The cheapest fix for the most embarrassing failure.
  • One trace id spanning every agent, so a failure is attributable rather than a shrug.
  • Grade the handoffs, not just the outcome. A system that ends in the right state having lost work in the middle is one bad day from ending in the wrong one.
  • Depth and global budget limits, so delegation cannot loop.

And the sentence that ties it together, worth saying almost verbatim: fan out to read, funnel to write — the extra agents contribute intelligence, not actions.
