The Agent Loop

The thing that replaces the scripted if/else. Twelve lines of code, five control dials, and every hard problem in production agents hiding in the ones nobody tunes.

~35 minThen the model gets plugged in

5.1 The loop is twelve lines

Before the mystique: every agent you have ever used — Claude Code, Cursor, a customer service bot, the thing we are about to build — runs this.

messages = [user_task]

while True:
    reply = model(messages, tools=TOOL_SPECS)   # ask
    messages.append(reply)

    if not reply.tool_calls:                      # it answered instead of acting
        break

    for call in reply.tool_calls:                 # act
        result = execute(call)
        messages.append(tool_result(call.id, result))

    if steps >= STEP_LIMIT:                      # or it never stops
        break

That is it. Ask, act, observe, repeat. Frameworks wrap it and harnesses decorate it, but underneath every one of them is a while-loop that calls a model, checks whether the response contains tool calls, runs them if it does, and stops when it doesn't.

In plain words

You are messaging a very capable colleague who has no memory between messages. Everything they know about the task, they know because it is in the thread you send them. Each time they reply they either say "I'm done, here's the answer" or "please run this for me and tell me what came back".

Your job is not to make them clever. It is to decide what goes in the thread, which tools they may ask for, and when to stop replying.

The interesting engineering is not the loop. It is the handful of decisions wrapped around it, and that is what this lesson is about.

5.2 What actually flows through it

A conversation with a tool-using model is a list of typed blocks, not a list of strings. Roughly:

  • user — the task
  • assistant — may contain text, reasoning, and one or more tool_use blocks, each with an id, a tool name and arguments
  • user — one tool_result block per tool_use, matched by id

Three things follow from that structure, and each one bites people:

  1. Every tool_use needs a matching tool_result. Miss one and the next call fails, or the model loses track of which answer belongs to which request.
  2. A model can emit several tool_use blocks at once — parallel tool calling. Your loop must handle a list, not one.
  3. Errors go back as tool_result too, not as exceptions. A failed tool is information the agent can act on. This is why Lesson 4 spent so long on error text.

Providers differ in naming — Anthropic's tool_use/tool_result, OpenAI's tool_calls and role:"tool" — but the shape is the same. Write your loop against your own small interface and adapt at the edge, exactly as we did with the three ATS providers.

5.3 First question: does this need an agent at all?

Anthropic's guidance is unusually blunt here, and it is the most valuable thing in their agents write-up: find the simplest thing that works. Most production "agents" should be workflows.

The distinction: in a workflow, you wrote the control flow. In an agent, the model decides the control flow. The second is more capable and much harder to make reliable.

PatternWhat it isUse when
Prompt chainingA fixed sequence of calls, each feeding the next, with programmatic gates between steps.The steps are known in advance.
RoutingClassify the input, send it to a specialised handler.Distinct kinds of request need different treatment.
ParallelisationSplit work across simultaneous calls, or run the same task several times and vote.Independent subtasks, or you want consensus.
Orchestrator–workersOne model decomposes and delegates, then synthesises.The subtasks are not predictable up front.
Evaluator–optimiserA generator paired with a critic, looping until quality passes.You have clear criteria and iteration genuinely helps.
AgentOpen loop; the model plans, acts, observes, and decides when it is done.The path cannot be predicted, and you can tolerate variance.

They compose: routing feeds a chain, an orchestrator wraps an evaluator–optimiser at the worker layer, parallelisation sits inside any of them.

The honest test

If you can draw the flowchart, write the flowchart. An agent is what you reach for when you genuinely cannot enumerate the steps — and you pay for that flexibility in latency, in cost, and in a far larger space of ways to fail.

Saying this in an interview marks you as someone who has run one in production rather than read about them.

5.5 Stopping: the dial that bites first

A loop with no termination logic either declares victory early or never stops. Four conditions, and you need all four:

  • Success — the model stops calling tools and answers. The intended exit.
  • Step cap — a hard maximum. Non-negotiable. This is what stops a looping agent draining your budget at three in the morning.
  • Budget — tokens or money. A step cap does not bound cost if each step is enormous.
  • No progress — the same call with the same arguments three times running means it is stuck, and ten more steps will not help.

How does it say it is finished?

Two designs, and it is a real fork.

Implicit — a turn with no tool calls means done. Simple, works everywhere, and it is what most loops do. The weakness: "let me explain what I found" looks identical to "I have finished the work".

Explicit — a finish(summary) tool it must call. More reliable, gives you a clean place to capture its own account of what it did, and makes "stopped without finishing" a distinguishable failure category rather than a silent one. The cost: one more tool, and the model sometimes forgets to call it.

In plain words

A contractor who stops arriving at your house has either finished or given up, and from your side those look identical until you inspect. A contractor who hands you a signed completion note has told you which one it was. The note can still be wrong — but now you can check it against the building.

Record the reason, always

"The agent finished" and "the step limit finished it" are completely different outcomes that produce identical-looking results. Store the stop reason on every run. It becomes a failure category for free, and it is the first thing you will look at when a score drops.

5.6 Context: the dial almost nobody tunes

Here is the number that reframes the whole subject. In a typical agent's context window, roughly 84% of the tokens are observation tokens — tool outputs, piling up turn after turn, never removed.

Think about what that means. The task, the tools, the reasoning and the answer are all squeezed into the remaining sixth. Everything else is a transcript of things the agent has already looked at.

In plain words

A detective's desk. The case file is two pages. Everything else on the desk is photographs from leads they already followed and dismissed — and more keep arriving, and nobody clears it. By the afternoon they are reading the desk instead of the case.

Four strategies, in increasing order of cost and risk:

  1. Do not create the problem. Bounded tool returns, pagination, pre-computed fields. Lesson 4 — and it is why our search returns 8 with a count rather than 34 with descriptions.
  2. Prune stale observations. Drop the body of old tool results, keep a one-line trace that the call happened.
  3. Mask rather than delete. Replace an old result with a stub the agent can re-fetch if it genuinely needs it.
  4. Summarise. Compact the history with another model call. Powerful, lossy, and a last resort — you are now trusting a summary nobody verified.
The counterintuitive finding

Pruned contexts can outperform full-history retention — not merely cost less, actually score better. Old context is not neutral: an agent holding the whole transcript will happily reason from a stale value it fetched nine steps ago instead of the current one.

"More context is better" is the intuition. It is wrong, and knowing that it is wrong is worth saying out loud in an interview.

This is the doorway into memory and context engineering, which gets its own module. For now the decision is narrower: what does the agent see each turn? Full history is the right starting point for short runs — but measure it, do not assume it.

5.7 When the model emits garbage

It will. These are the categories, and each needs a different response.

FailureLooks likeResponse
Malformed argumentsInvalid JSON, wrong type, missing required fieldReturn the validation error as a tool_result. It usually self-corrects in one turn.
Hallucinated idapp_999 — invented rather than taken from a resultAn error naming where valid ids come from. Never silently create it.
Wrong toolA plausible call, but the wrong tool for the requestNot a runtime error. Fix the descriptions — it is a design bug.
Unknown toolA tool name that does not existAn error listing the real names.
RunawayThe same call, the same arguments, over and overNo-progress detection, then stop. Do not let it burn the budget.
Premature stopAnswers in prose without doing the workThis is why explicit finish plus verification exists.

The governing principle from Lesson 4 applies with full force: a tool failure is information, not a crash. Hand it back and let the agent cope — then measure whether it did. "Error recovery" is a capability you can score.

Retry the transport, not the judgement

A 503 from your API is worth retrying automatically — the agent made a fine decision and the network failed. A validation error is not: retrying the identical bad call changes nothing. Retry infrastructure failures in your code; hand reasoning failures back to the model.

5.8 The system prompt, and treating it as code

An agent's system prompt does a different job from a chat prompt. It needs five things and not much else:

  1. Role and objective — who it is, and what "done" means.
  2. The rules that always hold — short, absolute, few. Long rule lists get partially ignored.
  3. How the tools work together — the sequencing knowledge that belongs to no single tool's description. "Read the profile before judging fit."
  4. How to handle failure — what to do when a tool errors, when nothing matches, when the task is ambiguous.
  5. The output contract — how it delivers the answer. In our case: shortlist it, do not describe it.

What does not belong: restating what a tool does. That is the tool's description, and duplicating it gives you two places to drift apart.

Prompts are versioned artefacts

This is the practice that separates a team that improves from one that churns. Prompts live in files, in git, with a version. Every eval result records which version produced it. Changing one becomes a change you can review, A/B against the suite, and roll back.

Sarvam's posting asks for exactly this — "prompt iteration workflows with versioning, A/B testing, and safe rollback" — and their Agent Engineer role puts it harder: "We treat agents as code. Not prompts someone tweaks in a console, but engineered artifacts: versioned, reviewed, and held to a regression suite."

In plain words

Nobody edits production SQL by typing into a console and hoping. It goes in a file, gets reviewed, and can be reverted. Prompts became load-bearing code about three years ago; most teams still treat them like console commands.

5.9 Determinism, and why you cannot have it

You can set temperature to 0. You will still get variation — batching, hardware and model-side nondeterminism see to that. Some providers offer a seed parameter; it reduces variance rather than removing it.

So stop trying. The environment is deterministic precisely so the agent does not have to be, and the correct response to a non-deterministic agent is measurement, not suppression:

  • Run every task several times and report the spread, not a single number.
  • Use pass^k when the agent takes real actions — all k runs must succeed.
  • Treat a score that moves by less than its own variance as unchanged.

Temperature 0 is still a sensible default for an agent: you want its most likely action, not a creative one. Just do not mistake it for repeatability.

5.10 Framework or hand-rolled?

LangGraph, the agent SDKs and the rest give you retries, tracing, state persistence and a community. They also put a layer between you and the twelve lines, which matters on the day something goes wrong at step nine.

The defensible position, and the one worth holding in an interview:

  • Hand-roll the loop at least once, so you know exactly what a framework is doing for you.
  • Adopt one when you need what it provides — durable execution, human-in-the-loop checkpoints, complex branching — not because it is what people use.
  • Never let a framework own your tool definitions or your evals. Those are yours, and they must outlive whichever library you are using this year.

You already know LangGraph. Hand-rolling this loop is not a step backwards — it is the thing that lets you say what LangGraph actually buys you.

5.12 Interview answers, out loud

"Walk me through how an agent actually works."
It is a while-loop. You send the conversation plus the tool schemas, the model replies with either an answer or one or more tool calls, you execute them, append the results, and go again until a stopping condition fires. The loop is trivial; the engineering is in five dials around it — tools, stopping conditions, context, verification and guardrails. Tools is the highest-leverage; context is the one almost nobody tunes.
"When would you not build an agent?"
Whenever I can draw the flowchart. If the steps are known, a workflow — a prompt chain, a router, orchestrator-workers — is cheaper, faster and far more predictable. An agent is for when the path genuinely cannot be enumerated, and you pay for that in latency, cost and a much wider space of failure modes.
"How do you stop an agent looping forever?"
Four conditions, not one: it stops calling tools, a hard step cap, a token or cost budget, and no-progress detection when the same call repeats with the same arguments. And I record the stop reason on every run — "it finished" and "the limit finished it" look identical in the output and are completely different outcomes.
"Your agent degrades on long tasks. Why?"
Usually context. Around 84% of a typical agent's window is tool output accumulating unpruned, so the task and the reasoning get squeezed into what is left — and stale observations actively mislead it, so it reasons from a value it fetched nine steps ago. I would bound tool returns first, then prune or mask old observations, and summarise only as a last resort. Pruned contexts can beat full retention outright, which surprises people.
"How do you handle a malformed tool call?"
Hand the validation error back as a tool result and let the model correct itself — it usually does in one turn. What I do not do is auto-retry a reasoning failure, because retrying the same bad call changes nothing. I retry transport failures in code and return judgement failures to the model. Then I measure recovery, because that is a capability worth scoring.
"Temperature 0 makes it deterministic, right?"
No. It reduces variance, it does not remove it — batching and hardware see to that, and seeds only help. So I make the environment deterministic instead, and measure the agent's variance honestly: several seeds per task, report the spread, and pass^k rather than pass@1 when the agent takes real actions.

5.13 What we build — four decisions

The scripted stand-in gets deleted. These are yours to make.

Decisions for our loop
  • Provider. Groq free tier (fast, free, weaker tool-calling) or Anthropic (best tool-calling, a few dollars). The loop is written provider-agnostic either way, so this is reversible.
  • What it sees each turn. Full history is the honest starting point for runs this short — but record token counts from day one, so that when we reach memory the before/after number already exists.
  • How it signals done. Implicit (a turn with no tool calls) or an explicit finish(summary) tool. I lean explicit: it gives a clean stop reason, and the summary is somewhere the judge can eventually look.
  • Malformed calls. Return the validation error as a tool result and let it retry — and count those retries, because schema-validity rate is one of the tool metrics from Lesson 4.

Plus one thing that is not a decision: the prompt goes in a file with a version, from the first line. Not later, when it matters. Every eval result we ever produce will carry that version, and retrofitting it means every number before the retrofit is unattributable.

Next

You answer the four. Then the loop gets written, the scripted agent is deleted, and for the first time the suite tells us something we did not already know — whatever that number turns out to be, it is the baseline everything else is measured against.
