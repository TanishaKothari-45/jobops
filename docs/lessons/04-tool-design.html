Tool Design

The tool layer decides more of your agent's behaviour than the prompt does. How to name, describe, parameterise and return — and how to test the result.

~35 minThen we rebuild search_postings properly

4.1 A new kind of contract

An API contract is between two deterministic systems. Both sides read the docs once, and from then on they behave identically forever.

A tool is a contract between a deterministic system and a non-deterministic one. Your code behaves the same every time. The thing calling it does not. It might call the wrong tool, invent an argument, ignore a required field, or call the right tool at the wrong moment — and it re-reads your description every single time it decides.

That difference is why tool design is not API design with different syntax. Anthropic's engineering guidance puts it exactly this way: tools are a fundamentally new paradigm — contracts between deterministic systems and non-deterministic agents.

In plain words

Writing an API is writing instructions for a machine. Writing a tool is writing instructions for a competent, fast, slightly distractible new colleague on their first day — who has no access to your internal wiki, cannot ask a follow-up question before acting, and will absolutely take an ambiguous instruction literally.

Everything in this lesson follows from that one image.

The claim that should change how you work

Anthropic reported that Claude Sonnet 3.5 reached state of the art on SWE-bench Verified after precise refinements to its tool descriptions — not a new model, not a new system prompt. The text describing the tools.

Sit with that. When your agent misbehaves next week, your instinct will be to edit the prompt. The higher-leverage edit is almost always in tools.py.

4.2 The six things the model reads

Every tool the model sees is six pieces of information. Each is an opportunity to be clear, or to be ambiguous.

  1. Name — how it refers to the tool, and the first thing matched against intent
  2. Description — what it does, when to use it, when not to
  3. Parameter schema — names, types, enums, which are required
  4. Parameter descriptions — the most-skipped, second-highest-leverage text you will write
  5. The return value — what comes back, which shapes every subsequent decision
  6. The error message — what it learns when things go wrong

Four of the six are prose. Tool design is mostly writing.

4.3 Naming

  • verb_noun, consistently. search_postings, get_application, draft_message — not a mix of findJobs, application_get and msgDraft.
  • Distinct verbs with distinct meanings. Pick one of search / find / lookup / query and never use the others. Overlapping names are the single biggest cause of wrong-tool selection.
  • Namespace when you have many. jobs_search, jobs_get, msg_draft. Anthropic recommends namespacing precisely because clear, distinct names stop agents confusing one tool for another.
  • The name should predict the return. get_application returns one; list_applications returns many. A model that guesses wrong from the name wastes a turn.
The test

Show someone only your tool names — no descriptions. If they cannot tell you which tool to use for "chase the ones that have gone quiet", the model cannot either.

4.4 The description

This is the highest-leverage text in your entire system, and most people write six words in it.

Anthropic's rule is the best one I know: write it the way you would explain the tool to a new hire — making explicit the context you would otherwise bring implicitly, including specialised query formats and any niche terminology.

A good description answers five questions:

  1. What does it do? One sentence.
  2. When should I use it? The situation, not the mechanism.
  3. When should I not use it? Almost always omitted — and it is what prevents wrong-tool selection.
  4. What are the side effects? Does it change anything? Is it reversible? Say so plainly.
  5. What are the gotchas? Units, formats, limits, terminology.
What most people write 
"Search job postings."
What the model needs 
"Search OPEN job postings you have not applied to yet. Returns the most recently posted matches first.

Use this to find new roles. Do NOT use it to look at applications you already sent - that is list_applications.

Matching is a case-insensitive substring on job title and company name, so 'AI' matches 'Applied AI Engineer'. It does not understand synonyms: 'ML' will not match 'Machine Learning'.

Read-only. Changes nothing."

The second costs four minutes and removes three classes of failure: wrong tool selection, wrong query format, and the model assuming semantic search when you built substring matching.

In plain words

"Search job postings" is a sign on a door that says Office. Technically true, and it tells a new starter nothing about whether to knock.

4.5 Parameters

  • Enums over free strings. status: "applied" | "rejected" is a constraint the model physically cannot violate. status: string is an invitation to invent "Applied", "APPLIED" and "in progress".
  • Describe every parameter. The type says what shape; the description says what it means. days: integer tells the model nothing about whether that is a lookback window or a delay.
  • Few required fields. Every required parameter is another chance to be wrong. Sensible defaults beat required arguments.
  • Flat beats nested. Models fill deeply nested objects badly. Prefer four top-level fields to one three-level object.
  • Avoid boolean traps. include_closed: true is fine; flag: true is not. If a boolean's name does not say what true means, it wants to be an enum.
  • Mind IDs. Models are poor at inventing identifiers and will happily hallucinate app_999. Either the id must have come from an earlier tool result, or accept a natural key instead — and every id parameter's description should say where the id comes from.
  • Always bound the output. A limit with a sane default, or pagination. An unbounded query is a context-window accident waiting to happen.

4.6 Return values — the underrated half

People design inputs carefully and then return whatever the database handed back. But the return value is what the model uses to decide everything it does next. It deserves more design than the input, not less.

Return what the next decision needs

Not the full row, not the ORM object. The fields that inform the next step, plus the id needed to go deeper.

Human-readable over raw identifiers

Anthropic is explicit: agents reason better with human-readable fields and simplified outputs than with raw technical IDs. Return "company": "Vantara Labs", not only "company_id": "co_007". A model can reason about a name; it cannot reason about a foreign key.

Pre-compute what the model is bad at

Language models are unreliable at arithmetic and date maths. If your rule is "7 or more days since last contact", do not hand over two timestamps and hope. Return "days_since_contact": 12. One line of Python removes an entire class of failure.

The one worth putting on a wall

Anything the model has to calculate, it will eventually calculate wrong. Anything you calculate, it never gets wrong. Move the arithmetic into the tool.

Token economy

Pagination, truncation and filtering, so the agent is not drowned in data. A tool returning 400 rows does not only cost money — it pushes the useful part of the context out of reach and degrades every later decision. When you truncate, say so inside the payload: "showing 10 of 47 - narrow the query or raise limit".

Include what the model cannot know

It has no clock. If dates matter, return "today" in the payload. It has no memory of your schema; if a status can only move in certain ways, say so in the result of the tool that changes status.

Stable ordering, always

Same reason as Lesson 2: unordered results make runs unrepeatable, and an unrepeatable run cannot be graded.

4.7 Errors are prompts

When a tool fails, its error message goes straight into the model's context and becomes an instruction. Treat it as prose written for the agent, because that is exactly what it is.

Useless 
404
"error"
"Invalid input"
null
Recoverable 
"No application app_999. Call list_applications to see valid ids."

"Draft msg_0003 was already sent - you cannot send it twice."

"subject must not be empty."
  • Say what went wrong and what to do instead. A good error names the recovery path.
  • Distinguish retryable from terminal. "Rate limited, retry in 30s" and "that record does not exist" need completely different reactions.
  • Never fail silently. A tool that returns an empty list on error teaches the agent there is nothing to do. That is worse than crashing.
  • Errors are information, not crashes. The environment hands the error to the agent and lets it cope — that is how you find out whether it can recover.

4.8 How many tools, and how big

Two failure directions.

Too many, or too overlapping → the model picks the wrong one. Selection accuracy falls as the candidate set grows, and falls fastest when tools overlap in meaning. This is measurable: the Berkeley Function-Calling Leaderboard's hardest category requires selecting the right m tools out of N offered.

Too coarse → the model cannot express what it wants. A single do_job_stuff(action, params) pushes all the ambiguity into a free-text argument, which is where ambiguity goes to become bugs.

Useful heuristics:

  • One tool per thing a user would ask for — not one per database table or REST endpoint.
  • Build high-leverage tools, not thin API wrappers. Anthropic's phrasing. If your agent always calls three tools in the same order, that sequence probably wants to be one tool.
  • If two tools could plausibly answer the same request, merge them, or sharpen both descriptions until they could not.
  • Consolidate list and detail carefully. A list_* that returns enough to decide, with get_* for depth, usually beats one tool with a verbose flag.
In plain words

A kitchen. Give a cook one implement called food_device and they cannot work. Give them ninety near-identical knives and they spend the service choosing. What they want is eight tools, each obviously for one job, with the differences visible at a glance.

4.9 Side effects and irreversibility

Band every tool, and design differently per band.

BandExamplesDesign implications
Read-onlysearch, get, listSafe to retry, safe to parallelise, cheap to be wrong. Say "read-only" in the description.
Reversible writedraft, update status, scheduleNeeds idempotency so a retry does not duplicate. An undo should exist.
Irreversiblesend, delete, payApproval gate. Idempotency key mandatory. Description must state plainly that it cannot be undone.
  • Idempotency keys. The caller supplies a key; calling twice with the same key does the work once. This is what makes retries safe and is the foundation of crash recovery.
  • Approval as a tool. Making request_approval a tool the agent must call — rather than a gate hidden in your backend — makes the agent's judgement about when to ask observable and gradeable. That is why our project has it.

4.10 How tools are evaluated

Where Lesson 3 and this lesson meet. Tool quality is measurable, and the vocabulary is worth a lot in an interview.

The BFCL categories

The Berkeley Function-Calling Leaderboard is the standard benchmark for tool use, and its categories are a ready-made test plan for your own tools:

  • Simple — one tool available, one call needed
  • Multiple — several tools available, pick the right one
  • Parallel — one tool, several invocations at once
  • Parallel multiple — the hardest: pick m right tools out of N
  • Irrelevance / hallucination measurement — irrelevant tools are offered and the model must decline to call anything
  • Multi-turn — several tool interactions in sequence

That fifth one is the one people forget. Knowing when not to call a tool is a measured capability — and it maps exactly onto our t02_nothing_is_stale task.

What to measure on your own tools

  • Tool selection accuracy — right tool for the request
  • Argument accuracy — right values, valid enums, no invented ids
  • Schema validity rate — what fraction of emitted calls even parse
  • Abstention — does it correctly do nothing when nothing is needed?
  • Error recovery — break a tool on purpose, see whether it adapts or gives up
  • Tool ablation — remove a tool and watch what breaks; tells you which tools carry the performance
  • Description A/B — change only the description, re-run the suite. The cheapest improvement loop in the project.
The loop that makes tools good

Write the tool → run the suite → read the failed trajectories → notice how the model misused it → fix the description or the return shape, not the prompt → re-run. Anthropic's guidance describes using agents themselves to exercise and refine tools this way. The failures tell you what your description failed to say.

4.11 Vocabulary you now own

tool schema
The JSON-schema description of a tool's name, purpose and parameters.
tool selection
The model choosing which tool to call. The commonest failure point.
abstention
Correctly calling nothing when nothing is needed. A measured capability.
irrelevance detection
BFCL's name for testing abstention with irrelevant tools present.
parallel multiple
Picking m correct tools from N. BFCL's hardest category.
idempotency key
A caller-supplied key making a repeated call do the work once.
tool ablation
Removing a tool to see what the agent can no longer do.
high-leverage tool
One that does a meaningful unit of work, not a thin API wrapper.
boolean trap
A flag whose name does not say what true means.
token economy
Paginating, filtering and truncating so results do not swamp context.

4.12 Interview answers, out loud

"How do you design tools for an agent?"
I treat the tool layer as the main interface the model reads, so most of the work is writing. Distinct verb_noun names so two tools can never plausibly serve the same request. Descriptions written like onboarding a new hire — what it does, when to use it, when not to, side effects, gotchas. Enums instead of free strings so invalid values are unrepresentable. And I design the return value as carefully as the input, because that is what the model uses for its next decision: human-readable fields over raw ids, pre-computed values for anything involving arithmetic or dates, bounded output with explicit truncation.
"Your agent keeps calling the wrong tool. What do you do?"
Read the failed trajectories first — find the first wrong call and what the model had in front of it. Usually two descriptions overlap, and the fix is a "do not use this for X, use Y" line in both. Then re-run the suite to confirm the change actually moved the number, because otherwise I am guessing. I reach for the system prompt last, not first.
"How do you stop an agent taking a dangerous action?"
Band the tools: read-only, reversible write, irreversible. Irreversible ones get an approval gate, an idempotency key, and a description stating plainly that it cannot be undone. I make approval its own tool rather than a hidden backend check, because that makes the agent's judgement about when to ask observable — and then the process grader can fail a run that skipped it even when the outcome looked fine.
"How would you evaluate tool use specifically?"
Selection accuracy, argument accuracy, schema validity rate, and abstention — whether it correctly calls nothing when nothing is needed, which BFCL measures as irrelevance detection and most people never test. Plus error recovery by deliberately breaking a tool, and ablation to find which tools actually carry performance. The cheapest loop is A/B-ing the tool description against a fixed task suite.

4.13 Now: one tool, done properly

We take search_postings and rebuild it against everything above. The decisions are yours:

Decisions for search_postings
  • What does a posting carry? Sponsorship requirement, remote or on-site, seniority, stack, salary band? Every field you add is something the agent can filter on — and something you can grade.
  • Filters in the tool, or filtering by the agent? The real fork. Filters make the agent's job easy and the eval boring; agent-side filtering is what you actually want to measure.
  • Does it know your profile? A get_profile tool, or profile baked into search's ranking? One is observable; the other is invisible.
  • What comes back per result — and what is pre-computed rather than left for the model to work out?
  • How is it bounded? Limit, pagination, truncation message?
  • What does "used correctly" mean — so the grader has something to check?
  • What are its failure modes, and what does each error say to the agent?

Then the tests: schema and behaviour tests for the tool itself, and tasks in the suite for whether the agent uses it correctly. Two different files, because they answer two different questions.
