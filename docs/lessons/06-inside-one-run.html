6.1 Why this chapter exists

Lesson 5 described the loop, the dials and the failure modes — all of it true, none of it attached to anything you could see. That is a hard way to learn.

So this chapter does the opposite. We take one run, twenty-one steps, from your repo, and read it. Every idea from Lesson 5 turns up again, but this time you can point at the line where it happens.

Nothing new is introduced until section 6.8. Until then it is just reading.

6.2 The setup

The task is s01_shortlist_five. The agent is told:

"Find me 5 roles worth applying to this week.
 Shortlist each one with a reason saying why it suits me."

It has twelve tools and a budget of thirty steps. The world is seed 42: thirty open roles it has not applied to, twelve of which genuinely qualify.

It does not know that twelve qualify. Working that out is the job.

In plain words

You have handed an assistant a filing cabinet and said "pick five jobs worth applying to". They cannot see the cabinet — they can only ask you for things from it, one request at a time, and you pass back what they asked for. What follows is the log of those requests.

6.3 Step 0 — it reads the profile

step 0
get_profile  {}
   →  Tanisha Kothari, 3 years, 9 target titles

The first thing it does is find out who it is shopping for. That sounds obvious. It is also graded — the policy read_profile_before_shortlisting fails any run that shortlists before this call happens.

Why grade something so obvious? Because an agent can shortlist five perfectly good roles without ever reading the profile, by guessing what she probably wants. The answer looks identical. The process is guessing.

This is the outcome/process split, live

There is a broken agent in the repo called shortlist_blind that skips this step and hardcodes its assumptions. On this task it scores outcome 3/3 — a perfect answer — and fails process, because it never looked.

That is the entire argument for grading the path as well as the result, in one example.

6.4 Step 1 — the number that changes everything

step 1
search_postings  {"limit": 25}
   →  showing 25 of 30

One broad search. Twenty-five results came back. Thirty matched.

Five roles exist that the agent has not seen. It has no way to know that — unless the tool tells it. This is exactly why Lesson 4 insisted the envelope carry matched alongside showing, plus a note in words:

"Showing 25 of 30. Narrow with query, seniority or country."

Without those two numbers the agent believes it has seen everything. It picks five good roles out of twenty-five, scores well, and never learns that a better one was sitting in the five it never got.

This actually happened

An earlier version of this agent did exactly that. On a different world it shortlisted four tier-2 roles while a tier-1 role sat in the truncated tail. The grader caught it, and the fix was to make the agent read the matched count and search again more narrowly.

Silent truncation is one of the most expensive bugs in agent work, because everything downstream still looks fine.

6.5 Steps 2–10 — nine more searches

Having seen 25 of 30, the agent runs one search per target title from the profile:

steps 2 – 10
search_postings  {"query": "Applied AI Engineer"}       → 1 of 1
search_postings  {"query": "AI Engineer"}               → 4 of 4
search_postings  {"query": "Agent Engineer"}            → 3 of 3
search_postings  {"query": "Forward Deployed Engineer"} → 0 of 0
search_postings  {"query": "Member of Technical Staff"} → 1 of 1
search_postings  {"query": "Research Engineer"}         → 3 of 3
search_postings  {"query": "Evaluation Engineer"}       → 0 of 0
search_postings  {"query": "LLM Engineer"}              → 0 of 0
search_postings  {"query": "Agentic Systems Engineer"}  → 0 of 0

Two things to notice.

It worked. The narrow searches found roles the truncated broad search had hidden. The fallback did its job.

Four of the nine returned nothing. Four steps, four round trips and four sets of tokens spent learning that this world has no Forward Deployed Engineer. The agent could not have known in advance — but it also never remembers, so it will spend those same four steps again on the next run.

In plain words

Ringing nine shops to ask whether they stock a part. Four say no. Tomorrow you ring all nine again, because you wrote nothing down.

6.6 Steps 11–20 — look up, then commit

Now it has candidates. From here it alternates: check the company, then shortlist the role.

steps 11 – 20
get_company        {"company": "Rill Networks"}      → series_a, 20.1 months ago
shortlist_posting  {"posting_id": "job_0013", ...}   → shortlist size 1

get_company        {"company": "Gradient Works"}     → series_c, 20.5 months ago
shortlist_posting  {"posting_id": "job_0019", ...}   → shortlist size 2

get_company        {"company": "Pale Blue Compute"}  → series_c, 9.2 months ago
shortlist_posting  {"posting_id": "job_0030", ...}   → shortlist size 3

get_company        {"company": "Gradient Works"}     → series_c, 20.5 months ago
shortlist_posting  {"posting_id": "job_0031", ...}   → shortlist size 4

get_company        {"company": "Sable Forecasting"}  → seed, 3.6 months ago
shortlist_posting  {"posting_id": "job_0034", ...}   → shortlist size 5

Look at the funding values: 20.1 months ago, 9.2 months ago. The tool computed those. It could have returned a date and left the model to subtract — and then "is that recent?" becomes arithmetic, which is the one thing a language model is reliably unreliable at. That is Lesson 4's rule, visible in a line of output.

And each shortlist_posting is a write. The answer is not a paragraph the agent composed. It is five rows in a table. That is what makes the next section possible.

6.7 The two states that decide the grade

The environment took a snapshot before the run and after it. Here they are:

before:  shortlisted: []
         shortlist_size: 0

after:   shortlisted: ['job_0013', 'job_0019', 'job_0030',
                       'job_0031', 'job_0034']
         shortlist_size: 5
         shortlisted_companies: ['Gradient Works', 'Pale Blue Compute',
                                 'Rill Networks', 'Sable Forecasting']

The grade is the difference between those two pictures. No transcript is read. No model is asked for an opinion. The question "did it do the right thing?" became "are these five rows the right five rows?" — and that is a question a machine answers instantly and identically every time.

6.8 Three things this run did badly

It passed everything. It is still wasteful in three ways, and none of them is currently graded.

1. It looked up the same company twice

Step 13 asks about Gradient Works. Step 17 asks about Gradient Works again and gets the identical answer. A whole round trip to learn something it was told four steps earlier.

Funding does not change in four steps. It does not change in four months. This is the cheapest cache imaginable and there is not one.

2. Four searches returned nothing, and it learned nothing from that

Next run, same four empty searches. The knowledge "this world has no Forward Deployed Engineer roles" exists for exactly as long as the run does.

3. Twenty-one steps to make five decisions

Ten searches, five lookups, five writes, one profile read. A tighter run does it in eight or nine. Every extra step is latency the user feels, tokens you pay for, and more context piling up — and remember from Lesson 5 that context is not neutral: old observations crowd out the useful ones.

The pattern behind all three

Each one is the same missing thing: the agent has no memory. Not memory in some grand sense — just the ability to remember something it learned four steps ago, or four runs ago.

That is the next module. And notice we needed no lecture to motivate it: we read one real run and the need fell out of the trace.

6.9 Where the model will sit

One honest thing about the run above: no LLM was involved. Every decision came from the scripted reference agent. The tools, the world, the grading and the trace are all real. The judgement was Python.

When the model is plugged in, these exact lines stay. What changes is who decides them:

  • Step 0 — the model decides to read the profile first. Or does not, and fails the policy.
  • Step 1 — it decides to search broadly first.
  • Steps 2–10 — it reads 25 of 30, decides that is not everything, and chooses which narrower searches to run. The most interesting decision in the run.
  • Steps 11–20 — it decides which five, in what order, and writes a reason for each.

The scripted agent exists so that all the surrounding machinery could be proven correct before a non-deterministic thing was placed in the middle of it. When the model goes in and the score moves, we will know the movement came from the model — because everything else already passed.

6.10 How to read any trace

Six questions, in order. They work on your agent, on someone else's, and in an interview when they put a trace in front of you.

  1. Did it gather before it acted? Reads before writes, or is it guessing?
  2. Was anything truncated? Look for a matched bigger than showing, and check whether it noticed.
  3. Where is the first wrong step? Not the last. Errors cascade, so the visible failure is usually downstream of the real one.
  4. What repeats? The same call twice means a missing cache. The same call five times means it is stuck.
  5. How did it end? Did it stop, or did the step limit stop it? Those look identical in the output and are completely different.
  6. What is the step count against the minimum? Twenty-one against a possible nine is a real finding, even on a passing run.
The habit worth building

Read the traces that passed. Everyone reads failures. Nobody investigates a pass — which is exactly why reward hacks and quiet waste live there. This run passed 9 of 9 checks and had three real problems in it.

6.11 Do it yourself

Print the same trace, then go looking:

.venv/bin/python scripts/run_suite.py shortlist_reference
.venv/bin/python scripts/run_suite.py shortlist_eager
.venv/bin/python scripts/run_suite.py shortlist_blind
.venv/bin/python scripts/run_suite.py shortlist_hoarder

Three things worth trying:

  • Run shortlist_blind and find the run where the answer is perfect and the process fails. Read why.
  • Run shortlist_hoarder and watch it run out of steps. A correct answer reached too slowly becomes no answer at all.
  • Run shortlist_eager on s03_nothing_qualifies — the world where nothing is worth picking and it picks five anyway.

6.12 Words from this chapter

trace
The recorded steps of one run, in order.
silent truncation
Results cut off without the caller knowing. Everything downstream still looks fine.
first wrong step
The earliest point a run departs from a correct one. Where debugging starts.
repeated call
Same tool, same arguments, twice. A missing cache - or a stuck agent.
state diff
Before and after, compared. The grade.
step budget
Steps used against the minimum the task needs.
