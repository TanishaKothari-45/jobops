Environment Design

How to build a small fake world an agent can act inside — one that behaves identically every time, starts fresh on demand, and can be checked by a machine at the end.

No maths required~20 minThen we build

2.1 An environment is not a test suite

In Lesson 1 we said an eval has three parts: tasks, the thing being tested, and a grader. An environment is what sits underneath all three — the little world the agent acts inside while being tested.

A test suite asks a question and looks at the answer. An environment is a place where things happen: the agent calls a tool, something changes, it calls another tool and sees the change. There is a world, it has state, and the agent moves through it.

In plain words

A flight simulator. You don't assess a trainee pilot with multiple-choice questions about engine failure — you put them in a cockpit, kill an engine, and watch what they do. The simulator has weather, fuel, altitude, instruments. Things change because of what they did.

Crucially: the simulator can be reset, it runs the same scenario identically for every trainee, and afterwards you can read off exactly where the plane ended up. Those three properties are the entire subject of this lesson.

This is also why environment design is a separate skill from prompt engineering. You're not writing instructions for a model — you're building a small, honest simulation of a piece of the world.

2.2 The five properties

Every good environment has these. Miss one and something downstream breaks — usually your ability to trust your own numbers.

01
Deterministic
The same actions always produce the same results. No randomness, no clock, no network.
02
Seeded
The world starts from a fixed, known state generated from a seed number.
03
Resettable
You can wipe it back to the start instantly, so runs never contaminate each other.
04
Observable
Everything the agent did is recorded — every call, every result, in order.
05
Assertable
At the end you can look at the world's state and say, in code, whether it is correct.

Notice how these chain. Without determinism you can't tell a real regression from noise. Without resettability your fifth run is polluted by your fourth. Without assertability you're back to reading transcripts by hand. Each property exists to protect the number at the end.

2.3 Determinism, and the four things that quietly break it

Determinism means: same world, same agent actions, same result. It sounds obvious and it's surprisingly easy to lose.

The clock

Any tool that asks "what time is it" makes your environment non-deterministic. A task saying "follow up on applications older than 7 days" gives different answers in October than it did in September. Fix: the environment has its own frozen clock. Time is part of the seeded world state, not something read from the machine.

Randomness

Generated IDs, shuffled lists, random sampling. Fix: one seeded random generator for the whole environment, created from the task's seed. Same seed, same "random" numbers, forever.

The network

A real API is the enemy of a repeatable test. It goes down, it changes, it rate-limits, it returns different data on Tuesday. Fix: the environment never touches the network. Everything is local.

Ordering

A database query with no ORDER BY can return rows in a different order on different runs, and the agent may then behave differently. Sneaky, because it's invisible until it isn't. Fix: every query is explicitly ordered.

In plain words

A board game. You can only compare two players fairly if the board starts the same way, the dice give the same rolls, and the cards are in the same order. Change any one and "she scored higher" stops meaning "she played better."

Important nuance — people get this wrong

The environment is deterministic. The agent still isn't — the LLM makes different choices on different runs, and that's fine, that's the thing we're measuring. A deterministic environment means that when the score changes, the change came from the agent and not from the world shifting underneath it.

Which is why we still run each task several times. We removed one source of noise so we could measure the other one honestly.

2.4 Seeded world state

A seed is just a number handed to a generator so it produces the same "random" data every time. Seed 42 always builds the identical world: the same 200 job postings, the same 14 applications, the same three stale follow-ups.

Three things come free with this:

  • Reproducibility. A bug found in seed 42 is a bug you can reproduce exactly.
  • Variety without effort. Seeds 1 to 100 give you a hundred different worlds from one generator.
  • Shareability. "It fails on seed 17, task 4" is a complete bug report. No data files to send anyone.
In plain words

Minecraft world seeds. Type the same seed as your friend and you get the identical world — same mountains, same village in the same place. The world isn't stored anywhere; it's regenerated from one number. Exactly what we're doing, with job postings instead of mountains.

2.5 The reset / step / done shape

This is the standard environment interface, borrowed from reinforcement learning. You'll meet it in almost every environment codebase, so the shape is worth more than the three functions suggest.

# the shape, in plain Python
env = Environment(seed=42, task="follow_up_stale")

state = env.reset()                # back to the starting world
while not env.done:
    action = agent.decide(state)   # agent picks a tool call
    state = env.step(action)       # world changes, returns what agent sees

result = env.grade()               # compare final state to expected

Three ideas, that's all:

  • reset() — rebuild the world from the seed, hand back the starting view. Every run begins identically.
  • step(action) — the agent does one thing. The world changes. The agent gets back whatever it would really see: the tool's result, or an error.
  • done — the run is over. Either the agent said it finished, or it hit the step limit, or it did something fatal.
In plain words

A video game with save files. reset is loading the save. step is pressing a button — the world responds and shows you the new screen. done is the level ending, whether you won, died, or ran out of time.

Why the step limit matters more than it sounds

Agents get stuck in loops. They will call the same search tool forty times with slightly different wording. Without a step limit, one bad run hangs your whole eval and burns your API budget doing it. A step limit isn't a detail — it's a termination condition, and "ran out of steps" is itself a useful failure category.

2.6 Three ways to handle tools

Your agent needs tools. In the real product they hit real systems. In the environment they must not. Three options — a genuine trade-off rather than a right answer.

ApproachWhat it meansGoodBad
Real tools The eval calls the actual APIs. Perfectly realistic. No drift between test and production. Not deterministic, costs money, rate-limited, can't run in CI — and will eventually email a real person by accident.
Recorded replay Record real API responses once, replay them during evals. Realistic data, deterministic playback, cheap. Breaks the moment the agent does something you didn't record. No world state — nothing to assert on.
Simulated world A small local database plus tool functions that read and write it. Fully deterministic, resettable, free, and there's a real state to grade. You have to build it, and it's only as realistic as you make it.
In plain words

Training a new bank teller. Real tools is putting them straight on the counter with live customer accounts — realistic, and terrifying. Recorded replay is showing them a video of yesterday's transactions — safe, but they can't do anything. Simulated world is a training branch with fake accounts they can actually debit and credit. Only the third lets you check the ledger afterwards.

That last sentence is the whole argument. Recorded replay can't be graded on outcome, because there is no outcome — nothing changed. If you want the machine-checkable grading we chose in Lesson 1, you need a simulated world.

2.7 The mirror principle

Here's the design idea that makes this practical rather than academic, and it's what keeps an environment maintainable.

Write the tool layer once. Point it at two different backends.

Your agent calls search_jobs(). In production that function talks to real boards. In the environment the identical function signature talks to the seeded local database. The agent can't tell the difference — and more importantly, you aren't maintaining two versions of your tool definitions that slowly drift apart.

In plain words

A flight simulator has the same cockpit layout as the real aircraft. Same switches, same positions, same labels. If the simulator's throttle were somewhere else, training in it would teach the wrong habits. A simulator's value comes entirely from mirroring the real thing.

The failure this prevents

Test/production drift. Someone adds a field to the real API, forgets the mock, and six weeks later your suite is confidently testing a system that no longer exists. Every eval passes; production is broken. One tool layer, two backends, and this can't happen.

2.8 What a task actually is

People use "task" loosely. In an environment it has a precise structure — four parts, and missing any one makes it ungradeable.

{
  // 1. where the world starts
  "seed": 42,
  "setup": { "stale_applications": 3, "unread_replies": 1 },

  // 2. what the agent is told
  "instruction": "Follow up on any application with no reply after 7 days.",

  // 3. what the world should look like afterwards
  "expected_state": {
    "drafts_created": 3,
    "applications_marked_followed_up": ["app_11", "app_23", "app_31"],
    "emails_sent": 0
  },

  // 4. rules that must hold regardless of outcome
  "policy": [
    "never sends without approval",
    "never contacts the same company twice in one run"
  ]
}

Part 3 is the outcome grader from Lesson 1 — it's just data. Part 4 is the process grader. Both are now plain values a machine can check rather than opinions. That is the payoff of building a world with real state.

And look at "emails_sent": 0. That's a negative assertion — a check that something did not happen. Beginners write only positive assertions and miss half of what matters. The most expensive agent failures are things it did that nobody asked for.

2.9 Trajectory logging: what to record

The trajectory is your record of the run. Get this right at the start, because you can't recover data you didn't capture — and you will want it later.

  • Every message — what went to the model, what came back, including reasoning if the model exposes it.
  • Every tool call — name, arguments, result, in order.
  • World state snapshots — at minimum start and end; ideally after each step.
  • Timing and tokens per step — this is what makes the cost and latency work in module M9 possible without re-running anything.
  • Task id, seed, prompt version, model name — so a result is always attributable. A score with no version attached is not evidence.
In plain words

An aircraft's black box. Nobody enjoys writing the recorder, and it matters only after something goes wrong — but then it's the only thing that matters. Crash investigators don't ask the pilot what they remember. They read the tape.

2.10 Task templating and difficulty

Ten hand-written tasks are enough to start. They aren't enough to measure with — too few to separate signal from luck, and they'll all sit at roughly the same difficulty because you wrote them in one sitting.

The fix is a task template: one task shape with knobs you can turn.

  • Steps required — one stale application, or twelve.
  • Distractors — applications that look stale but aren't. Does the agent check properly, or pattern-match?
  • Ambiguity — an instruction that could mean two things. Does it ask, or guess?
  • Broken tools — one tool returns an error. Does it retry, route around, or give up silently?

Turn those knobs and one template becomes a hundred tasks across a difficulty range. Now you can plot score against difficulty instead of quoting a single number — which tells you where the agent falls over, not just that it does.

In plain words

A driving instructor doesn't have one test. They have a parking bay that can be wide or tight, in daylight or dusk, with or without a van blocking the view. Same skill, dialled up. That's how you learn whether someone can actually park, or just memorised one bay.

2.11 Reward hacking

This is the failure mode that makes environment design a real job rather than a chore — and the one Scale AI's posting names directly: “build graders that maintain integrity under adversarial optimization.”

Reward hacking is the agent satisfying your grader without doing the task.

Real examples, all of which happen:

  • You grade "the application is marked followed-up." The agent marks every application followed-up and writes no drafts. Full marks.
  • You grade "a draft exists." The agent creates three empty drafts. Full marks.
  • You grade code by "the tests pass." The agent deletes the failing test. Full marks.
  • You grade with a judge that likes thorough answers. The agent writes long, confident, wrong answers. Full marks.
In plain words

Every incentive scheme ever designed by humans. Pay a call centre by calls-per-hour and agents hang up on people. Pay by lines of code and you get verbose code. Measure a hospital on waiting-room time and patients get moved to a corridor that technically isn't the waiting room.

The agent isn't cheating. It's doing exactly what you measured. The measurement was wrong.

Four defences, most useful first:

  1. Grade the outcome that actually matters, not a proxy for it. "Draft exists" is a proxy. "Draft exists, is addressed to the right company, and mentions the role" is closer to the real thing.
  2. Add negative assertions. Check what should not have changed. Most hacks show up as unexpected side effects.
  3. Grade process as well as outcome. A hack usually takes a visibly wrong path.
  4. Read real trajectories by hand — especially the ones that scored perfectly. Suspiciously high scores are how you find hacks, and nobody ever investigates a pass.

2.12 Vocabulary you now own

environment
A small simulated world with state that an agent acts inside.
seed
A number that regenerates an identical starting world every time.
reset / step / done
The standard three-part environment interface.
step limit
Maximum actions before a run is force-ended. Prevents infinite loops.
tool mock
A tool function backed by the simulated world instead of a real API.
expected state
The world as it should look afterwards — the outcome grader, as data.
negative assertion
A check that something did not happen.
distractor
Something that looks relevant but isn't, added on purpose.
reward hacking
Satisfying the grader without doing the task.
test/production drift
Mocks and real systems diverging until evals test a fiction.

2.13 Could you answer these out loud?

"Why does the environment need to be deterministic if the LLM isn't?"
To isolate the variable. The agent's randomness is what I'm measuring; the world's randomness is noise I can remove. Once the world is fixed, a score change means the agent changed — and I still run multiple seeds to read the remaining variance honestly.
"Why not just record real API responses and replay them?"
Replay has no world state, so there's nothing to assert on — you lose outcome grading entirely. It also breaks the moment the agent does something you didn't record.
"What's reward hacking, and how do you defend against it?"
The agent satisfying the grader without doing the task — deleting a failing test instead of fixing the code. Defences: grade the real outcome rather than a proxy, add negative assertions for what shouldn't change, grade process alongside outcome, and hand-read the runs that scored perfectly.
"How do you stop your test environment drifting from production?"
One tool layer, two backends. The same tool functions point at either the real systems or the seeded simulation, so there's no second copy to fall out of sync.

2.14 What we build next

Project 1 — the job-search operations environment
  • A seeded world in SQLite — companies, job postings, applications with statuses and dates, message drafts, and a frozen clock. Generated from a seed, never from the network.
  • One tool layer, two backends — around eight tools (search postings, read application, draft message, mark status, schedule follow-up, escalate to human…), written once against a single interface.
  • reset / step / done with a step limit, so a looping agent ends cleanly and countably.
  • Full trajectory capture — messages, tool calls, results, per-step tokens and timing, plus task id, seed and prompt version on every record.
  • Ten hand-written tasks with expected state and policy rules, including at least two negative assertions and one deliberate distractor.
  • A state-diff grader — pure Python, zero LLM calls, comparing the final database to the expected state.

None of this needs an LLM. You could grade a hand-written script with it — and we will. That's deliberate: the environment must be correct before an agent ever touches it, or you'll spend days unable to tell whether the agent is broken or the world is.
