Lesson 10 · Agent Env Lab

Retrieval and RAG

Five stages, each with its own class of bug. How to tell a retrieval failure from a generation failure — and the measured ladder that takes a retrieval system from mediocre to good.

~40 minSources at the end

10.1 What retrieval is for — and when not to

Retrieval exists to put the right few hundred tokens in front of a model that has no idea your data exists. That is the whole job. Everything else is implementation.

Which means the first question is not "how do I build RAG", it is do I need retrieval at all? Four alternatives, each better than RAG in its own case:

Instead of RAGUse whenWhy it wins
A database queryThe answer is a row, not a passage"How many applications are open?" is SQL. Embedding it is absurd and less accurate.
Stuffing the whole documentThe corpus is small and stable — one policy doc, one specNo pipeline, no chunking bugs, no retrieval failures. Costs tokens; caching makes that cheap.
A tool callThe data is live and structuredAn API returns today's truth. An index returns whenever you last rebuilt it.
Fine-tuningYou need a behaviour or format, not a factFine-tuning teaches style and structure. It is a poor way to teach facts, which change.
In plain words

Retrieval is a library. If the answer is in one book you already own, hand over the book. If the answer is a number in a ledger, look it up in the ledger. You build a library when there is genuinely more material than one person can hold and you cannot predict which page will matter.

Worth saying in an interview: the most common failure in RAG projects is building one for a problem that was a SQL query.

10.2 Five stages, five classes of bug

A retrieval pipeline is five steps, and a failure at any one looks identical from outside — a wrong answer. Knowing which stage broke is most of the skill.

StageDoesFails as
1. ChunkSplit documents into retrievable unitsThe answer is split across two chunks, so neither one answers the question
2. Embed & indexTurn chunks into vectors, store themDomain vocabulary the embedding model never saw; a stale index
3. RetrieveFind candidates for a queryThe right chunk exists and is not returned
4. RerankReorder candidates by true relevanceThe right chunk is returned at rank 19 and gets cut
5. GenerateAnswer using the chunksThe right chunk was supplied and the model ignored or contradicted it
The single most useful diagnostic habit

When an answer is wrong, ask one question first: was the correct chunk in the context?

If no — it is a retrieval bug, and nothing you do to the prompt will fix it. If yes — it is a generation bug, and nothing you do to the retriever will fix it.

People burn weeks tuning chunk sizes to fix what was a prompt problem, and rewriting prompts to fix what was a chunking problem. One check tells you which half of the system to work on.

10.3 Chunking decides everything downstream

The most consequential and least glamorous decision. A chunk is the unit that gets retrieved, so a badly cut chunk cannot be rescued by anything later in the pipeline.

The core trade-off

  • Small chunks — precise, high signal density, and they lose the context that made them meaningful. A paragraph reading "this does not apply to enterprise customers" is dangerous without the section it qualifies.
  • Large chunks — keep context, and dilute it. One relevant sentence in two thousand tokens drags the embedding toward everything else in the chunk.

Overlap is the usual mitigation: chunks share a window so a boundary cannot cleanly sever an idea. It costs storage and creates near-duplicates, which is one more thing for the reranker to sort out.

The strategies, in increasing sophistication

StrategySplits onGood forWeakness
Fixed sizeToken countA baseline; uniform corporaCuts mid-sentence, mid-table, mid-idea
RecursiveParagraph, then sentence, then wordThe sensible default for proseStill blind to meaning
Document structureHeadings, sections, list itemsDocs, specs, policies — anything with real structureNeeds a parser per format; sections vary wildly in size
SemanticWhere the topic shifts, detected by embeddingsUnstructured long-form textCosts an embedding pass over everything; boundaries still surprise you
Late chunkingEmbed the whole document first, then split and poolLong documents with long-range dependenciesNeeds a long-context embedding model
Agentic chunkingA model chooses boundaries from structure and intentHeterogeneous corpora where one splitter cannot fit allExpensive, non-deterministic, needs its own evaluation

Late chunking is worth understanding because it inverts the usual order. Classic pipelines chunk then embed, so each chunk embedding only ever saw its own text. Late chunking embeds the full document first and splits the token sequence afterwards, pooling each slice — so every chunk embedding saw the whole surrounding document. Long-range dependencies survive, which is exactly the failure that sinks chunk-then-embed.

In plain words

Cutting a film into clips. Cut every 90 seconds and you slice through the middle of scenes. Cut on scene boundaries and each clip stands alone. Watch the whole film first and then cut, and you can label each clip with what it means in the story — which is what late chunking buys.

10.4 Embeddings

  • Model choice matters more than dimensionality. A model that has seen your domain's vocabulary beats a larger one that has not.
  • Dimensions trade recall against cost. More dimensions mean better separation, more storage, slower search. Many current models allow truncating dimensions with graceful degradation — measure rather than assume you need full width.
  • Changing model means re-embedding everything. Vectors from different models are not comparable at all. Budget that migration before you choose, because you will want to switch.
  • Symmetric vs asymmetric. Queries are short, documents long. Retrieval-trained models expect that asymmetry, often with separate query and document prefixes. Using them wrongly costs accuracy silently.
What embeddings are genuinely bad at

Exact identifiers. "job_0041", an error code, a part number, a surname. Embeddings capture meaning, and an identifier's meaning is that it is that exact string — a property vectors represent poorly. This is not a tuning problem; it is what the representation is for. It is also the whole reason for the next section.

10.5 Dense, sparse, hybrid

MethodMatches onFindsMisses
Dense (embeddings)Semantic similarityParaphrase: "how do I get money back" → the refund policyExact tokens: an error code, an id, a rare name
Sparse (BM25)Keyword overlap, weighted by rarityExact terms, identifiers, jargonAnything phrased differently from the document
HybridBoth, scores fusedBoth of the aboveNeeds two indexes and a fusion rule

They fail in opposite directions, which is why combining them works so well. The standard fusion is reciprocal rank fusion — combine by rank position rather than raw score, because the two systems' scores are not on comparable scales.

In plain words

Two librarians. One knows what every book is about, and will find you something on grief when you ask about bereavement. The other has memorised the catalogue and will find the book whose title contains exactly "ISBN 0-19-853453". Asking only one is how you fail half your queries.

10.6 Contextual retrieval — the measured ladder

The clearest published demonstration that these techniques stack, and the numbers are worth memorising because they let you argue with evidence rather than taste.

The problem being solved: a chunk reading "revenue grew 3% over the previous quarter" is useless in isolation. Which company? Which quarter? Naive chunking strips exactly the context that made the sentence meaningful.

Contextual retrieval prepends a short, chunk-specific explanation to each chunk before it is embedded and indexed. Anthropic measured the effect on top-20 retrieval failure rate:

Baseline — embeddings only5.7%—
+ contextual embeddings3.7%−35%
+ contextual BM25 (hybrid)2.9%−49%
+ reranking1.9%−67%

Three things to take from that. Each layer compounds rather than replacing the one before. Hybrid search alone is worth roughly as much as the contextual trick. And reranking — the cheapest change on the list to implement — removes a further third of what remained.

10.7 Reranking

Retrieval is optimised to be fast over millions of documents, which means it is approximate. Reranking is a second, slower, more accurate pass over the shortlist.

The mechanism matters. A bi-encoder — ordinary embedding search — encodes query and document separately and compares vectors, which is what makes indexing millions of chunks possible. A cross-encoder reranker reads query and document together and scores the pair directly. Far more accurate, far too slow for the whole corpus, exactly right for the top 50.

The standard shape: retrieve 50–100 candidates cheaply, rerank them, keep the top 5–10 for the model.

In plain words

Hiring. A keyword filter over four thousand CVs, then a human actually reads the fifty that survive. Nobody reads four thousand, and nobody hires straight from the keyword filter. Two stages, different jobs, different costs — that is the whole design.

Why reranking is usually the best first upgrade

It needs no re-indexing, no re-embedding and no change to chunking. It is a component you insert. For most teams with a mediocre RAG system it is the largest quality gain available per hour of work — and the ladder above puts a number on it.

10.8 Retrieval vs long context

With million-token windows, "just put everything in" is a real option, and sometimes the right one. The honest comparison:

RetrievalLong context
CostScales with what you retrieveScales with everything, every call — though caching changes this sharply for stable corpora
AccuracyDepends on the retriever finding itDegrades with length — the context rot from Lesson 7, at every increment
FreshnessAs fresh as your last index buildAs fresh as what you pasted in
AttributionYou know which chunk it usedYou do not, without extra work
Scale ceilingEffectively unbounded corpusA hard limit, reached quickly in enterprise data

The rule: long context for a corpus that is small, stable and entirely relevant — one policy document, one file, one contract. Retrieval when the corpus exceeds the window, changes often, or when you need to cite the source. That last one is underrated: in a regulated setting, attribution is not optional.

And they combine: retrieve the relevant documents, then use a long window to reason across all of them at once.

10.9 Agentic retrieval

The shift that matters most for agent work: retrieval stops being a fixed pipeline step and becomes something the agent decides to do.

Classic RAG: one query in, one retrieval, one answer. Agentic retrieval: the agent searches, reads what came back, notices a gap, searches again with better terms, and stops when it has enough. A loop, not a stage.

What it buys:

  • Query reformulation. The user's words are often not the corpus's words. The agent can try several phrasings — exactly the "search several titles separately" advice from Lesson 4, generalised.
  • Iterative narrowing. Broad search, then targeted follow-ups based on what the first pass revealed.
  • Knowing when to stop — or when to say it cannot find the answer. Abstention, which is a measurable capability.

What it costs: more steps, so more latency and quadratically more tokens (Lesson 9), plus non-determinism in what gets retrieved — which means you can no longer evaluate the retriever in isolation. Retrieval decisions are now part of the agent's trajectory and have to be graded there.

The 2026 framing worth knowing

With very large context windows widely available, the question has shifted from "what do I retrieve?" toward "what do I chunk into retrievable units in the first place?" — because the constraint moved from how much you can fit to what a usefully retrievable unit actually is.

10.10 Measuring it: two different questions

The most important structural point in this lesson. Retrieval metrics and generation metrics answer different questions, and conflating them is why so many teams cannot debug their own systems.

Retrieval metrics — did we find it?

  • Context recall — of the information needed to answer, how much appeared in the retrieved chunks? Below 100% means something required is simply missing, and no prompt fixes that.
  • Context precision — of the chunks retrieved, how many were relevant? Low precision dilutes the signal and invites reasoning from noise.
  • recall@k — is the right document in the top k? The plainest version of the same question.
  • MRR / nDCG — rank-aware: not just whether it was found, but how high. This is what reranking moves.

Generation metrics — did we use it properly?

  • Faithfulness — what proportion of claims in the answer can be verified against the retrieved context? Your hallucination detector.
  • Answer relevance — did it actually address the question asked?
  • Answer correctness — if you have gold answers, the ordinary thing.
Read them together, or they lie to you

High recall, low faithfulness → retrieval works, the model is ignoring it. A prompt or model problem.
Low recall, high faithfulness → the model is faithfully using chunks that do not contain the answer. A retriever problem wearing a disguise.
Both low → start with retrieval. Fixing generation on top of bad retrieval is building on sand.

Faithfulness and context precision are the pair that disagree most often in practice, and their disagreement is where the diagnosis lives.

One caution connecting back to Lesson 3: most of these metrics are themselves computed by an LLM judge over decomposed claims. Every judge caveat applies — bias, variance, cost — and almost nobody calibrates them. A RAGAS score with no kappa behind it is a directional signal, not a measurement.

10.13 Interview answers, out loud

"Walk me through designing a RAG system."
First I'd check it needs to be RAG — if the answer is a row it's a database query, and if the corpus is small and stable I'd stuff it and cache it. Assuming retrieval is right: structure-aware chunking with overlap, contextual retrieval so chunks keep the context naive splitting strips, hybrid dense plus BM25 because they fail in opposite directions, then a cross-encoder reranker over the top 50. And I'd measure retrieval and generation separately from day one, because otherwise you cannot tell which half is broken.
"Your RAG system gives a wrong answer. How do you debug it?"
One question first: was the correct chunk in the context? If no, it's a retrieval bug and no prompt change fixes it — I'd look at recall@k and context recall, and work out whether it's a chunking problem or an identifier problem. If yes, it's a generation bug — faithfulness will be low, and the fix is in the prompt or the model, possibly too many chunks so the right one got lost in the middle. People lose weeks tuning chunk size to fix prompt problems.
"Why hybrid search? Isn't semantic strictly better?"
No — they fail in opposite directions. Embeddings capture meaning, so they find paraphrase and miss exact tokens; an error code or an id has no meaning beyond being that exact string, which vectors represent badly. BM25 does exact terms and misses rephrasing. Anthropic's contextual retrieval numbers show it concretely: contextual embeddings alone took top-20 failure from 5.7% to 3.7%, adding contextual BM25 took it to 2.9%, and reranking to 1.9% — 67% overall, each layer compounding.
"Context windows are a million tokens. Is RAG dead?"
No, for three reasons. Accuracy degrades with length — Chroma measured it at every increment, not just near the limit. Enterprise corpora exceed any window. And retrieval gives attribution: you know which source the answer came from, which in a regulated setting isn't optional. Long context is right for a small stable corpus, especially with caching. Often the answer is both — retrieve the relevant documents, then use a long window to reason across all of them.
"What's the cheapest improvement to a mediocre RAG system?"
Add a reranker. No re-indexing, no re-embedding, no chunking change — you insert a cross-encoder over the top 50 candidates. In Anthropic's published ladder it removed a further third of the remaining failures after hybrid search. Best quality gain per hour of work available.
"How is retrieval different inside an agent?"
It stops being a pipeline stage and becomes a decision. The agent searches, reads, notices a gap, reformulates, searches again, and decides when it has enough — or that it can't find it, which is abstention and worth measuring. The cost is more steps, so more latency and quadratically more tokens, plus you can't evaluate the retriever in isolation any more: retrieval decisions are part of the trajectory and have to be graded there.

10.14 What this means for our project

Decisions
  • Our search is deliberately not semantic — it is a substring match, and the tool description says so explicitly. That is honest tooling: the agent knows synonyms will not work and compensates by searching several titles. A semantic search that quietly missed "ML Engineer" for a query of "Machine Learning" would be worse and harder to debug.
  • When we add semantic matching, it is hybrid from the start — job titles are full of exact tokens (company names, posting ids) that embeddings handle badly.
  • The agent already does agentic retrieval. Reading matched against showing and issuing narrower follow-up searches is query reformulation. It just happens over a database rather than a vector store.
  • Retrieval quality gets its own metric, separate from task score. Otherwise a drop in shortlist quality is ambiguous between "it searched badly" and "it judged badly" — and those need different fixes.
  • Abstention is already in the suite — s03_nothing_qualifies tests exactly the "found nothing, answered anyway" failure, in shortlisting form.
